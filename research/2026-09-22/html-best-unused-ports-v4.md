## Decision

The best next port is **a source-grounded, operator-reviewed memory worker** followed by **relevance retrieval over approved business evidence**. A third valuable boundary is **accepted-claim materialization with reversible lineage**. These add the missing observation and continuity pipeline to the existing relational runtime without importing Maya's companion identity. Voice-mechanics observation and provider spend control are useful supporting projects; neither is an emotion classifier or a ready Azure voice benchmark.

### Flow 1: utterance to durable memory, traced end to end

The later Room path is the strongest **implemented code boundary**, with a deployment caveat. `src/room/RoomApp.tsx` / `roomApi.ts` send a follower message after the join screen records a distinct memory answer. `api/_room-surface.js:joinRoom` stores that answer; `roomSay` chooses `roomMemoryAdapter` only for the non-Meera Room agent and, when memory is enabled, logs the user's turn before reply, recalls scoped facts, and logs the answer afterward. `api/_room-memory-authority.js:ROOM_MEMORY_LOG_SQL` binds raw rows to follower, epoch, agent, person and device. Its batch query selects **user** turns only, up to 32, still in the current memory epoch. `api/consolidate-sweep.js` discovers lag, claims a lease, and calls `runMeteredRoomMemoryConsolidation` only in its separate `room_only` mode. The wrapper reserves Azure spend, re-reads the source snapshot before model dispatch, settles usage or marks it uncertain, then calls `runRoomMemoryConsolidation`. The model may return zero to twelve proposals. `validateRoomMemoryProposal` requires a real source ID and exact contiguous quote; `ROOM_MEMORY_COMMIT_SQL` checks those again under source/authority locks and atomically creates an episode, fact/observation rows, and consumed cursor. Recall joins back through the cited episode and current follower epoch. Correction and retraction SQL preserve lineage.

This is stronger than `main:api/memory.js:opRemember` for a company port. `opRemember` performs model extraction and has a self-output laundering guard, but its graph-node summary is not required to be an exact user quote and it contains companion interior/wants. The later Room branch was designed for quoted durable memories. Its `ROOM_MEMORY_CONSOLIDATION_ENABLED = true` does **not** mean unattended production runs are enabled: `_room-memory-consolidation.js:roomMemorySweepEnabled` also requires `CONSOLIDATE_SWEEP_MODE=room_only` and `CONSOLIDATE_ROOM_DEV=1`; `consolidate-sweep.js` defaults to dry run unless the live gate is set. `evals/room-memory-authority/run.mjs` checks model-await withdrawal, epoch ABA, edited/deleted source, exact quotes, and writer/reader predicates with doubles and static SQL checks; its own first line says the doubles do not parse PostgreSQL. The source migration `db/migrations/159_room_memory_authority.sql` and live SQL need separate verification. No current deployment status follows from the branch tip.

Port scope: use this workspace's organization/contact/session IDs and existing proposal/review UI, keep assistant turns in the transcript but exclude them as evidence for customer facts, and preserve exact turn ID plus character span. The current transcript's receipt timestamps do not prove when speech occurred, so do not derive call timing or an emotion label from them. A worker needs a durable source revision and a compare-and-set commit, not the source's Room follower or replica tables. Azure-only dispatch must use the supplied resource and a configurable budget. On edit/revocation, approved derived rows and any embeddings must be invalidated before the next session snapshot.

### Flow 2: saved evidence to reply, traced end to end

On the companion call, `src/components/useCallEngine.ts` starts `memory.recallForCall` while ringing, allows a bounded wait, then compiles the voice prompt with the returned memory and relationship bundle; a later result updates the **next** compile site rather than mutating an already-open Live session. `src/engine/memory.ts:runRecall` posts `op:"recall"` to `/api/memory` with a two-second client bound. `api/memory.js:opRecall` starts keyword/background, person lookup, semantic, activity, relationship and self-bundle legs concurrently. The semantic leg embeds the query and runs a **person-filtered exact** halfvec scan over non-invalid, non-retracted facts with agent scope on both vector and fact. `rrfFuse` merges query hits and a co-citation hop; activity and watched evidence remain separate so their meaning is not collapsed into one rank. The renderer has a 6,000-character T5 budget, and `buildTrace` returns IDs, counts, elapsed time and bytes instead of duplicating memory text. `src/engine/compiler.ts:compile` receives already-filtered bundles; `evals/recall/run.mjs` covers tokenizer, SQL/read shape and forget coverage, but is offline and partly static.

For business agents, retrieve from approved chunks **after** organization, agent-release and contact/audience predicates, and return source IDs/revisions plus excerpts. A search hit must never authorize disclosure by itself. Keep a keyword path when embeddings fail, cap total added turn latency, and instrument whether an old relevant source was missed. The source's `api/_embed.js` hardcodes a 1,536-dimension OpenAI embedding model through Azure first and then paid OpenRouter; that fallback violates this workspace's paid-provider rule. The source's dyadic salience, spaced resurfacing and companion phrases should not become customer-ranking policy. This workspace's SQLite fallback also lacks `halfvec`; a portable first port can use indexed lexical retrieval and add an Azure/Postgres vector lane only where supported.

### Flow 3: reviewed claim to reversible state

`src/studio/PersonModelStudio.tsx` displays proposed claims for owner review. `api/_person-model.js` records an accept/reject decision and calls `materializeAcceptedClaimToRelationalOs` for accepted claims or `retractClaimRelationalMaterialization` for revoked ones. The materializer's `ELIGIBLE_CLAIM` checks the **latest** decision, approved claim status, exact citation edges, source readiness, consent and validity window. `acceptedClaimRelationalCommitment` hashes proposal, decision and dyad identity. The writer re-runs eligibility under lock before inserting an episode/fact with an idempotence marker; source erasure can find derivatives through its marker. The code explicitly does **not** infer a relationship-state event from a general claim. `evals/experience-compiler/relational-materializer.mjs` and `run.mjs` are contract evidence; source history still warns live runtime/SQL validation is pending.

For the SaaS, replace owner/replica identity with organization, contact or account, reviewer, allowed audience, agent release and source revision. Keep business fact approval distinct from an affect hypothesis and distinct from authorization to act. The source's accepted Person Model claim should not be silently treated as a company policy or promise.

**Contradiction detail:** `main:api/consolidate.js:finalizePerson` creates a new fact and invalidates an older active fact when the same normalized `name` has a different `body` (around lines 785–815); a sampled entailment judge can refute unsupported new facts and halt a run above its authored rate threshold. This is useful lineage machinery, but same-name/different-body is a **replacement heuristic**, not semantic contradiction detection. Two conflicting claims with different names can coexist, and a new changed plan may simply be later in time. The Room correction route is firmer for a user-originated correction: `ROOM_MEMORY_CORRECT_SQL` writes an exact new statement and episode, then supersedes the chosen old fact without asking a model to reinterpret the replacement; `evals/room-memory-correction/run.mjs` checks that shape offline. In a business port, explicit customer corrections should take this path, while inferred conflicts go to review with both citations and validity times.

## Emotional and voice opportunities, with limits

The existing `lib/voice/relational-runtime` already ports caller-led repair, honorific, moment gating, cause-bound concern and current-turn behavior. More regex variants would add little. The genuinely unused semantic input is the **source-cited extraction proposal** in Flow 1: a model can notice a stated need, concern, preference or correction in varied wording, while exact quoted spans, human review and source revocation prevent a guess from becoming durable truth. `main:api/consolidate.js:finalizePerson` also extracts episodes and affect tags, but its call tag `voice_v0` explicitly means inference from *words* spoken on a call, not acoustic analysis, and its companion taxonomy is not a business evaluation. Use a transient `caller-stated concern` or `uncertain hypothesis` channel, not a hidden emotion score.

The successor's `api/_experience-compiler/expression-observation.js` blob `ffeabcbc…` defines a closed schema for measurable delivery features, not moods. `mirror-expression.js` blob `0cfb9782…` derives turn duration, speech rate, token count, script transitions and optional WAV RMS; all rows bind source/turn/consent and expire after 24 hours, with `may_claim_inner_emotion:false`. `api/mirror-call.js` calls it after settled ASR and treats failure as a collect-only side lane. `evals/mirror-expression-observation/run.mjs` verifies the units, source hash, TTL and no-inner-emotion contract. This is a bounded future port for voice pacing and interruption research after microphone capture is verified here. Script transitions are not language identification; RMS is not perceived emotion. Its purpose is owner **training** consent, which cannot be reused for customer-call analytics.

`src/engine/observation.ts` blob `ce38fb4f…` offers a different, pull-only cited **text** observation: one citation minimum, shape lint, no read without current-turn signal words, invalidation and decay. The later Vyakti `api/memory.js` calls `matchObservations` and `api/consolidate.js` calls `decayObservations`; Room's atomic commit writes `vy_observation` directly. I found no direct caller of its exported `writeObservation` or `promoteObservation` outside generated engine exports. This is useful as a bounded retrieval contract, not proof that all authored observation lifecycle functions are in use. `evals/self/observation.mjs` checks the helper behavior.

The source's `src/voice/liveCall.ts` and `evals/echosim/*` remain useful for exclusive audio ownership, acoustic interruption and echo simulation. This workspace has provider-neutral browser sessions and a Maya speech-text/Despina profile, but microphone, STT and barge-in are still unverified here. Port a traceable state/turn contract first; tune thresholds on the actual Azure/Gemini browser devices. The later `api/_voice/hindi-text-frontend.js:buildVoiceTextPlan` offers a separable pronunciation plan and bounded Roman-Hindi transforms; source tests and benchmark plans do not establish present voice quality. Keep transcript text separate from spoken text and rate its code switching, prosody, first audio and interruption in real calls.

## Provider, dependencies and rejection calls

`api/_provider-budget.js` and `_room-memory-consolidation.js` have a durable reserve/begin/settle/uncertain-spend pattern worth porting for Azure inference and background extraction. `api/_dialogue/providers/azure-foundry.js` validates endpoint, response model, JSON and usage. The earlier `_gkeys.js`/`_lanes.js` are already mapped in [provider-reuse-map](../../docs/provider-reuse-map.md); their Google/OpenRouter lane order and optional billed Google route are **rejected** under the Azure-only paid constraint. Adopt task-aware routing and error classes only with an explicit Azure spend invariant. Do not import source model names, assumed prices or account quota claims.

This workspace's `lib/server/db.ts` supports SQLite by default and Postgres through `pg`; the source Room implementation requires Postgres-specific CTEs, row locks, triggers, `jsonb`, leases and migrations. The source semantic leg requires `halfvec` and a matching embedding deployment. Its root `package.json` is private and no root `LICENSE`, `COPYING` or `NOTICE` appears at the inspected `main` and Vyakti tips; the root project owns both repositories, but an exact code copy into a separately distributed product still needs an explicit rights/dependency review. No source credential values were read. Static code and authored evals prove boundaries were written, not that live migrations, current Azure deployments, consent, budget or human voice quality are working.

## Port acceptance gates

1. A changed or revoked source while Azure extraction is awaiting a response commits zero memory, consumes no cursor, and remains retryable; empty extraction commits no invented memory. The reviewed proposal cites the exact user-turn span, and approval cannot silently change its source revision.
2. Retrieval tests include paraphrases with zero shared keywords, old relevant documents, same-name contacts in two organizations, revoked chunks, prompt-injection text inside a source, embedding failure and budget truncation. A citation ID must resolve to an authorized current source at response time.
3. Corrections and erasure remove every derived fact, vector and relationship cue; replay of the same reviewer decision is idempotent. Model hypotheses remain proposals and never move permanent trust, claim that work completed, or grant action authority.
4. Provider tests prove every paid model task uses only the supplied Azure resource, logs usage and uncertain outcomes, and has bounded deadlines from the first outbound request. Real-device voice claims require actual microphone, ASR, interruption and listener review beyond offline fixtures.
