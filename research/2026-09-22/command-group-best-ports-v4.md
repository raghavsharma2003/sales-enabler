# Command Centre + Vyakti-GroupAI: best remaining ports (v4)

**Date:** 22 September 2026. **Method:** read `research/command-centre-audit.md`, `research/vyakti-audit.md`, `research/architecture-reuse.md`, `docs/implementation-status.md`, `docs/reuse-provenance.md`, and the current product/state first; then refreshed both source repos with `git fetch origin --prune` and inspected their remote-tip trees. This is a read-only source audit. I did not run source apps/tests, contact providers, import customer data, execute send scripts, or read credentials. The 21 Command Centre named heads and three Vyakti named heads remain at the SHAs recorded below. Blob IDs are Git object IDs at those exact refs, not new test results.

The requested product path is **messy company/customer data → extraction and entity resolution → source-governed company brain → personalized email/WhatsApp/browser-voice campaigns → replies, feedback, owned work and measured outcomes**. The current application already has authenticated organization scope, manually authored/approved brain sources, customers/consent, agent version snapshots, campaign preflight and manual run outcomes, and a partial GroupAI world/room/audience capsule with internal Azure text turns (`lib/platform/customer-ops.ts`, `agents.ts`, `campaigns.ts`, `groups.ts`, `group-turns.ts`). It has no file/connector ingestion, canonical account resolution, retrieval index, automatic campaign dispatch, external channel identity, provider receipts, automated feedback extraction or scheduled recovery worker. Its GroupAI simulated speaker is operator-selected; room turns are not external participant messages.

## Ranked ports

### 1. Reviewed ingestion and entity resolution — **pattern rewrite**, first product gap

Command Centre `origin/main` `c8fd321407d7b628b7e79d105887b6a182760100`: `lib/import-reconciliation.ts` blob `111cd1fa2432cc7e5bcb6880047c1975dba9f6b2`; `lib/import-reconciliation.test.ts` blob `e9778adbae24b7233690c4005e067144d9819e9d`; `components/import/import-wizard.tsx` blob `dacc1f9aff94566fd616008006c86172fc747ab9`; `supabase/schema.sql` blob `8a4841c5083b3c5bd3d57c079907f871491ace8f`; `docs/data-hunt/SPEC.md` blob `9b3cd63ceb103e8a3b18bee575ef44d3790c19eb`. The reconciliation/test blobs are identical on the unmerged hardening head, so that branch adds nothing to this candidate.

Copy the **workflow**: preserve raw input and normalized proposal, show candidate matches and field changes, quarantine ambiguity, assign a reviewer, and record the selected merge/new/reject decision. The source wizard does this for one flat `leads` table and creates `import_review` tasks. Build the new pipeline around tenant-scoped source artifacts, extracted passages and field proposals; explicit `company`, `person`, `contact_point` and relationship identities; source/permission/licence/freshness status; deterministic import-run and row IDs; and reviewer-approved writes. An AI extraction may propose a value, but the exact source span and current authority must travel with it. Never let a duplicate guess silently overwrite the authoritative CRM field.

Do **not** transplant `reconcileLeadRow` as the authoritative matcher: it removes legal suffixes and non-ASCII letters, uses the last ten phone digits, can derive a company domain from an employee email, scans all leads in memory, and uses fixed `0.74`/`0.04` fuzzy thresholds. These are useful fixture-level tests for exact/domain/fuzzy/ambiguous routing, not a cross-country identity policy. The data-hunt spec is a quality rulebook, not an importer or permission to load its candidate CSVs.

### 2. Cited, audience-bound context and memory promotion — **actual package port plus new authority adapters**

Vyakti `origin/claude/vyakti-cloning-platform-aq05n4` `451de5a6a7017dc76eaac69fe551203dc94753d2` (these package blobs equal `origin/codex/relational-core` `4bae159631ca3f18da0ede48596f593a55b6728c`): `packages/relational-core/src/memory.ts` blob `814cdd0e10aa0427bddbb56d82d7bcd0b133389b`; `privacy.ts` blob `c2f228269bb3b103ff368884d19c8a75fd2f4ace`; `context-assembler.ts` blob `4c8f2c80da4ce435ecc6342e4c1909b3c3f6b7aa`; `packages/context-capsule/src/authorization.ts` blob `395dabda286626b447d89821e52f0324bea27479`; `compiler.ts` blob `047bd763e8c221af3d2513767f306aa60fbc3252`; `compiler.test.ts` blob `5a9a66002642b5064a77b9c740837dba3b73e253`; privacy matrix test blob `867093d43eb73011107a548a83e742ee0740c659`.

Extract the pure schema/authorization/compiler/hash package with its tests rather than recoding its deterministic whole-block budgeting, recipient/purpose/act binding and manifest verification. Map `world` to an authenticated organization or case boundary only where appropriate. Keep group room epochs distinct from campaign cohorts. Add a trusted source adapter that turns reviewed transcript/document passages into typed memory proposals with source event IDs, epistemic status, valid/expiry times, owner and allowed recipients. Promotion is an explicit review transaction; a private student/parent/customer statement must never become organization-wide knowledge by summarization. Retrieval must first filter by tenant, identity, lifecycle, current source authority and scope, then issue authorized blocks; revalidate again before model egress and outbound use. Correction/revocation must invalidate derived blocks and previously materialized retrieval projections.

This is **not** a complete retrieval port. Vyakti's `context-assembler.ts` sorts supplied candidates and authorizes disclosure; it does not search documents, enforce its `MemoryRecord.lifecycle.expiresAt` by itself, or prove a candidate's current source. `context-capsule` verifies an issued manifest, not whether an upstream extractor told the truth. The current `lib/platform/groups.ts` already covers a narrow operator-attested room subset and `group-turns.ts` pins replies to the current snapshot; replace/extend carefully to avoid two divergent privacy authorities.

### 3. One durable action ledger for channels — **actual runtime contract, new persistence and adapters**

Vyakti same Claude/codex heads: `packages/delivery-runtime/src/runtime.ts` blob `c9aa0ae96d305fe269ce23ea5c5f5cfdbc3abd4f`; `types.ts` blob `e48c0afad5a112da54a8ab136b511204844ff2f7`; `runtime.test.ts` blob `ccd69ce6cd816caccdc182c93d0ef1773e25c4eb`; `packages/postgres-runtime/src/delivery-repository.ts` blob `d28e5e8b5caa3d2897eb4c8a54edc2e43c1c0cd4`. Command Centre `origin/main` `lib/cold-email/sequence-engine.ts` blob `38df3687ec07a0912433f265ce42b8b3bef7ecff`; `lib/email-jobs.ts` blob `07ab3a21f4a88bd1ea2ebee4c65780b3a0104844`; `lib/whatsapp/executor.ts` blob `c37c235bdfb59602c8e114d5220e820824f49e56`. The unmerged `origin/claude/context-project-review-0x0i6g` `d288e75c14dce50150f9787149a79e5fe4bd271c` has WhatsApp executor blob `3e12f5b101b5f842f71fc62d9fbb73dcc038151c`, adding conditional row claim and daily-cap check.

Port Vyakti's `DeliveryRuntime`/transport capability interface and adversarial cases, then implement an organization-scoped repository for the app's chosen DB. Every approved campaign recipient action needs a stable intent/idempotency key, immutable payload digest and authority snapshot, due time, lease/fence, dispatch-time consent/suppression/budget check, provider acceptance/receipt, and `ambiguous`/reconciliation/dead-letter state. The runtime test specifically covers crash after provider acceptance without a duplicate resend and stale lease fencing. For email SMTP, provider-native idempotency and authoritative reconciliation may be unavailable: keep ambiguous sends pending human/provider reconciliation rather than retrying as if failure were certain. The current app's manual campaign outcome is not a delivery receipt.

Command Centre's sequence engine is more mature than its older batch job path, but its hardening branch is **78 commits behind main** and removes newer audience paths while patching send-time scope. Do not merge it wholesale. Its WhatsApp `sending` claim avoids overlap but has no lease expiry/recovery, and daily caps are read before concurrent sends; adapt the intent and cap transaction, not the file. Preserve channel-specific rules (Meta templates and 24-hour service windows, email suppression, verified browser call admission), while the ledger has one common outcome vocabulary.

### 4. Inbound replies and feedback into owned work — **adapter patterns, classifier rewrite**

Command Centre `origin/main`: `lib/cold-email/imap-poller.ts` blob `785ea70bf6e5c8d5f21a4c46c0caca762108d3d2`; `reply-matcher.ts` blob `a21d2bbcf5679977b99e9e7cc9bdcbb6fd4c5993`; `reply-classifier.ts` blob `daee858a9b03257ece7aee50a339d660515efd4b`; `reply-classifier.test.ts` blob `1cbd9d5bb1d4ca0c4412e70c55c25d5ab9610a99`; `lib/outreach-workflow.ts` blob `bfb27071fca320d338308828e880e65e98db68be`; `app/api/whatsapp/webhook/route.ts` blob `37d0eae6eeb03f07c88c85354bc9c7e7354433ac`. The IMAP poller captures provider message IDs, filters system/warmup mail, upserts inbound messages, associates sends and classifies; outreach workflow projects reply/bounce/open events into lead history and tasks.

Implement tenant/provider-scoped inbound event dedupe and explicit correlation to a dispatched intent. Matching by `In-Reply-To`/`References` is a useful starting algorithm; Command Centre's sender-address fallback may attach a reply to the wrong campaign when a person received multiple messages, so mark such matches uncertain for review. Extract sales intent and service-feedback themes as **proposals** with exact reply/transcript spans, model/run version, confidence and counter-evidence. Human review can accept a field update, create an owned action, correct a claim or reject it. Close the loop only when task and customer outcome evidence are recorded. Keep the selected Azure paid inference path; do not copy the source's CBAM-specific prompt or provider fallback order.

### 5. Group coordination and source consumption — **small code seam plus domain rewrite**

Vyakti same Claude/codex heads: `packages/follow-through-core/src/source-consumption.ts` blob `b647128cb6958084e1ee748bc78df744311b17b5`; `packages/postgres-runtime/src/follow-through-source-ports.ts` blob `a153bc3945e65106f45c4d1feb37a2ad0f5e5557`; its test blob `f792b0b9d2d2521bf06bb5c711cd64d08d60f2d9`. The preclaimed transaction port accepts one exact source event/decision/aggregate/version binding and rejects a changed or repeated binding; replay is backed by durable rows. That small contract is a good direct port for converting a reviewed customer statement into **one** commitment or company-brain claim without duplicate promotion on replay. The rest of `follow-through-core` models social multi-party consent and unanimous completion; business tasks, staff assignment and customer notification need new domain rules. Do not treat GroupAI's social-world ownership as a blanket staff access grant.

For durable model-input provenance, Vyakti's `db/migrations/012_turn_context_provenance.sql` blob `8f69e8601d2be1240253295d7dfe8d3891f13815` and Claude-tip `019_shadow_preprovider_provenance.sql` blob `4a2adec6b7d952086df6a40a33b632a8341ed877` (verify blob `db832519934fb1681be294540474567e467ed822`) demonstrate append-only cited event/witness records and pre-egress revalidation. Migration 019 is expressly **shadow-pilot-only** and does not authorize delivery, business actions or reviewer promotion. Translate its constraints into app schema/tests when adopting PostgreSQL; do not run this SQL against the current generic `entities` store.

### 6. Provider and webhook safety gates — **small snippet, integration rewrite**

Command Centre hardening head `d288e75c14dce50150f9787149a79e5fe4bd271c`: `lib/secure-compare.ts` blob `400a54426eb1dde2fe8a9f96fca1b8f4235bd463` is a tiny directly portable constant-time comparison helper; `app/api/integrations/webhooks/[provider]/route.ts` blob `421fbaa5e168d140c6384044fddd62a6769860e0` fails closed on a missing configured generic webhook secret. Port the guard into each new provider adapter with signature verification, replay/idempotency checks and tenant connection lookup. Do not use the branch as proof all webhooks are safe: even its `lib/whatsapp/cloud-api.ts` still returns true when `WA_APP_SECRET` is unset. The current app has no inbound Meta/SMTP provider surface yet, so this gate belongs with the adapter implementation.

## Execution order and proof

Build an import/source ledger first so every company fact has a reviewable origin. Port the GroupAI capsule kernel against that trusted authority and prove revocation/correction blocks retrieval and model input. Then add the shared action ledger and one outbound/inbound email path; expand to WhatsApp after the receipt and suppression contract is exercised. Add feedback extraction as a proposed, cited write and show the resulting owner task and measured outcome on the customer journey. The minimum end-to-end fixture should include two similar companies, two contacts at one company, a private customer statement, an ambiguous import row, a revoked fact, an approved campaign, provider acceptance followed by worker crash, an inbound reply with uncertain attribution, and a reviewed feedback action. Assertions should cover tenant isolation, no private-context leak, no duplicate send, accurate provider/outcome state, and the source trail from claim to completed work.

Source test files prove authored coverage only; this audit did not rerun them. The exact candidate list and disposition are in `command-group-port-ledger-v4.json`.
