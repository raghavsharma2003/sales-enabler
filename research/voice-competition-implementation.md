# Voice competition and implementation research

Research date: 2026-09-21 (Asia/Kolkata). Scope: a browser-first, voice-first customer-operations product with a permissioned relational company brain. Phone is explicitly a later channel. This is implementation research, not a vendor scorecard: a documented capability is not evidence of quality on our customers, and vendor benchmarks are retained as vendor-reported measurements.

## Decision framing

The differentiated product should be the **customer record and action system**, not a claim to own the most human voice. Buy or compose realtime voice initially; retain a provider-neutral session contract; build durable identity resolution, sourced relationship state, permissions, human handoff, and evaluation traces ourselves.

The browser MVP needs: WebRTC/browser audio; streaming captions; immediate local barge-in mute; server-authoritative action permissions; an append-only conversation/event log; a contact/account/case/opportunity graph; source-cited memory with expiry; and an operator command centre that can correct, approve, or take over. Do not turn inferred affect into a customer attribute or decision. Store only user-stated needs/concerns and operational signals, with source turn, confidence, access scope, and review/expiry state.

## Evidence labels

* **Documented claim**: a current first-party documentation statement, linked below.
* **Vendor-reported measurement**: a first-party number, with configuration and corpus unknown unless specified.
* **Unknown**: no public primary source found that establishes the point. It is a test requirement, not a negative finding.

All sources were accessed on 2026-09-21. Prices and included services change often; obtain a written quote and price a complete call/session, including STT, TTS, LLM, telephony, storage, egress, evaluation, and concurrency.

### Reading the comparison

Vapi, Retell, Bland and ElevenLabs reduce time-to-first browser prototype; they also put meaningful execution paths behind a vendor. LiveKit and Pipecat give more control and make a relational product boundary clearer, while increasing delivery responsibility. Hume is a voice/interaction candidate, not a reason to store emotional labels. There is no evidence here that one option wins every metric.

## Recommended implementation: browser-first relational operations loop

1. **Realtime edge.** Browser obtains a short-lived, tenant-scoped room/session token. It sends microphone audio via WebRTC and renders partial captions locally. On speech start while the agent is speaking, mute queued playback immediately; the server later decides whether it was an acknowledgement or a material interruption.
2. **Turn controller.** Keep VAD, endpoint detector and backchannel classifier separate. Persist `speech_started`, `turn_candidate`, `turn_committed`, `assistant_audio_started/stopped`, `interruption` and a monotonic timestamp. Make timing observable per stage; never present an aggregate latency without its distribution.
3. **Context assembly.** Resolve identity using explicit identifiers and confidence, then fetch only permissioned current records: active case/opportunity, recent interactions, user-stated concerns, outstanding tasks and policy/knowledge fragments. Every retrieved fact needs a source, owner, effective date and scope.
4. **Policy/action gateway.** The model proposes typed operations (`search_customer`, `create_task`, `update_case`, `book_slot`, `handoff`). Gateway validates tenant/actor/record permissions, field allowlist, required consent, idempotency key and preconditions. Separate read from write. A spoken interruption never silently cancels a submitted write: expose pending/committed/cancelled state and compensate only when safe.
5. **Human command centre.** Show live transcript, confidence, current customer record, sources, proposed actions, pending tools, consent, handoff reason and an edit/takeover control. Store reviewer corrections as grounded feedback, not unqualified self-memory.
6. **Event ledger and projections.** Store immutable audio/transcript/action events with retention class; derive searchable CRM projections and summaries. A summary is replaceable; the source event and approval history are the audit trail.
7. **Privacy defaults.** Explicit recording notice/consent when required; minimize audio retention; isolate tenant data; encrypt and scope recordings/transcripts; deletion/export flows; human-visible source attribution; no training/model-improvement use without explicit contract/consent. Confirm requirements with counsel for every deployment jurisdiction.

## Integration flows

### Voice to company brain

`browser session → live transcript/events → identity resolution → scoped context query → model proposal → policy gateway → CRM/tool write or human approval → event ledger → CRM projections + follow-up task`

The identity resolver must allow **unresolved** and **ambiguous** results. Never attach a call to a similarly named person just to keep the conversation flowing. A shared family/company phone number must create a disambiguation step before revealing private context.

### External CRM connector

`source webhook/poll → signature + replay validation → normalized external event → idempotency/deduplication → mapping + conflict policy → append ledger → projection update → optional outbound acknowledgement`

Use source-of-truth ownership per field. Example: Salesforce owns opportunity stage; the voice product owns transcript events and proposed next actions; a human-approved mapping may update stage. A vendor's post-call sentiment field is an observation, never an authoritative customer fact.

## Benchmark protocol (no results claimed)

Use the 20 stable scenarios in [`../evals/scenarios.json`](../evals/scenarios.json). Run exact same persona, knowledge, tool stubs, browser/network profile, voice, language and policy gateway across candidate stacks. Publish configuration versions, date, region, hardware, sample count, and exclusions.

Measure at least:

| Dimension | Definition | Pass rule must be set before run |
| --- | --- | --- |
| End-of-turn latency | final meaningful user speech end → first audible assistant sample; report p50/p90/p95 and decomposed STT/turn/LLM/TTS/network stages | Product-specific threshold; never infer from vendor claim |
| Barge-in | user speech start → playback muted; rate of correct material interruptions and rate of false interruptions on acknowledgements/noise | Separate the two error types |
| Turn accuracy | human-labelled continuation vs completion; false cut-offs and excessive waits by language/accent/noise | Stratify by scenario and language |
| Task correctness | expected safe response/action; no unsupported promise or unauthorized record disclosure/write | Must be 100% for safety-critical scenarios before pilot |
| Relationship correctness | stated concern recalled only with source and permission; correction supersedes stale memory | Human reviewer checks source and expiry |
| Tool safety | duplicate, stale or corrected requests do not create duplicate/incorrect writes | Use tool stubs plus idempotency log |
| Operability | all turns/actions have trace IDs, timestamps, configuration and outcome; takeover works | Audit sample before customer rollout |

Use at least three repetitions per deterministic audio fixture and larger, consented human samples before making product claims. Counterbalance conditions and have reviewers blind to provider where practical. Treat vendor upgrades as a new candidate configuration. No scenario result should be filled in until it is actually run and reviewed.

## Selection gates for the first pilot

1. Can it supply browser audio, captions, raw event/timing export and immediate barge-in behavior?
2. Does it pass the permission, correction, identity ambiguity and no-duplicate-write scenarios with our gateway?
3. Does it meet predeclared latency/turn-quality targets on consented target-locale traffic, including Hindi-English mixed turns if that is the market?
4. Are DPA, retention/deletion, subprocessors, residency, incident terms and BAA/sector needs acceptable?
5. Can we pin/replay configuration enough to investigate a complaint? If not, use it only behind a replaceable adapter or reject it for production.

## Explicit unknowns to close with trials or contracts

* A vendor's language count does not establish intra-sentence code-switch accuracy, local names, numbers, or target accents.
* A vendor's interruption claim does not establish backchannel false-positive rate in our browser, microphones and noise.
* Soft fillers and expressive voices can improve perceived warmth or create pressure; evaluate appropriateness with humans and compliance reviewers.
* Sentiment/emotion labels should not determine eligibility, priority, pricing or sales pressure. Evaluate response behavior, not hidden-state inference.
* Published per-minute or character prices omit differing components and commercial terms. Model full-session cost and peak concurrency from a dated quote.

It is not yet a demonstrated choice for the browser-first relational product until it passes browser transport, acknowledgement-vs-interruption, mixed-language, tool-cancellation and data-governance tests. Its self-hostable repository is a potential escape hatch, not a claim that self-hosting will be cheaper or easier.

### Resulting command-centre requirements

The overlapping market makes the build boundary sharper:

1. **Canonical relationship ledger.** Immutable event + source + effective/expiry time + tenant + access scope. Customer-visible CRM projections are derived, correctable views.
2. **Typed, permissioned action plane.** Every tool carries schema, resource/action scope, preconditions, idempotency key, risk class, actor, evidence bundle and a state (`proposed`, `awaiting_approval`, `committed`, `failed`, `superseded`).
3. **Voice-aware operational trace.** Join browser audio/timing, transcript revision, turn decision, retrieval, model/config, tool call and human takeover under one trace ID. Generic agent logs do not make an interruption investigation possible.
4. **Human control with a useful decision packet.** Approvers see target record, exact payload/diff, source/effective dates, policy result, confidence/ambiguity and what a rejection changes. Approval is bound to the payload hash and expires; an altered action needs a new decision.
5. **Connector discipline.** Maintain inbound webhook replay protection, signatures where available, field-owner rules, conflict queues and outbound receipts. Where a provider only supplies source-IP verification, add an application-level shared-secret/signature scheme where possible and validate every request independently.

These requirements complement rather than replace CRM/enterprise-agent platforms. The practical wedge is not “one brain that knows everything”; it is a customer-operating record that can show what was heard, what source supported it, who was allowed to act, what was approved, and what actually changed.
