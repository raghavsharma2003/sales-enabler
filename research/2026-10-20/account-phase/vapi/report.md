1. THE BIG PICTURE
Vapi is a sparse, versioned configuration store plus a call runtime and an event bus. The buyer stores assistants, tools and squads; a call names one (or sends one inline) with an inline customer; the runtime emits webhooks that carry the whole call object; costs come back as typed lines. Everything an Indian operator needs around the call (contacts, consent, suppression, windows, retries, business outcomes) is absent from the data model (AP-12, AP-27, AP-58).

3. CALL LIFECYCLE AND STATE MACHINE
POST /call | campaign dispatch | inbound ring | web call -> start checks (assistant resolves, number resolves, customer valid, subscription, credits, fraud check, concurrency; each failure is a call.start.error-* reason) -> scheduled -> queued -> ringing -> in-progress -> ended; forwarding branch for transfer/handoff; side states not-found, deletion-failed. Types: inboundPhoneCall | outboundPhoneCall | webCall | vapi.websocketCall; transport sip|pstn. endedReason has 638 values: 300 call.in-progress.error-*, 270 pipeline-error-*, 20 call.start.error-*, 5 call.ringing.error-*, 2 forwarding, 2 other call.*, 39 plain (customer-busy, customer-did-not-answer, voicemail, silence-timed-out, exceeded-max-duration, assistant-ended-call, twilio-failed-to-connect-call, sip-outbound-unallocated-number...). All engineering codes keyed to a provider; none is a business outcome. Campaign status: scheduled | in-progress | ended | cancelled | archived; a blocking campaign.predial webhook can veto each dial (errors, timeouts, non-boolean replies mean no call). Calls stamp assistantVersion; an explicit split picks the version (docs say sticky by caller number: vendor-claimed). (AP-23 to AP-27)
