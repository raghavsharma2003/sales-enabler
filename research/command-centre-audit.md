# Command Centre repository audit

Repository: `https://github.com/raghavsharma2003/command_centre.git`  
Clone: `research-sources/command_centre`  
Audit date: 2026-09-21  
Audit baseline: `origin/main` at `c8fd321407d7b628b7e79d105887b6a182760100`

## Scope and method

I cloned the repository, read its root `AGENTS.md`, then read `docs/AGENT-CONTEXT.md` and the recent tail of `docs/SESSION-LOG.md` as required by that file. I enumerated every remote branch ref, including the 20 non-main heads and `origin/main`; the symbolic `origin/HEAD` ref is excluded from the count. For each head I recorded the full SHA, compared `origin/main...<ref>`, inspected unique code and operational documents, and traced merged historical commits where the tip is already contained in `main`.

This was a static repository audit. I did not install dependencies, start Next.js, call production APIs, run project scripts, execute customer-data harvesters, render PDFs, or run tests. Large branch CSVs were inspected structurally (schema, counts, reports, and quality notes) rather than reproduced row by row; that avoids copying contact records into this report. No customer names, email addresses, phone numbers, tokens, or credentials are reproduced here.

## Product readout

The repository is a statically implemented, CarbonSettle-specific internal operating system with a broad amount of production-shaped code; runtime behaviour was not tested in this audit. It is not yet a general SaaS “company brain”. The durable product core is a CRM and multi-channel revenue-operations console; the CBAM domain rules, campaign copy, pricing/proposal content, and importer/exporter research are tightly coupled to one company.

The implementation that is present in `main` includes:

- A Next.js 16 / React 19 App Router application with Tailwind 4, Supabase Postgres, Vercel cron routes, and a custom component library (`package.json`, `app/`, `components/`, `lib/`).
- A lead CRM with pipeline stages, owner filtering, next-action dates, phone history, activity log, import reconciliation, audit metadata, proposal pricing fields, and follow-up prioritisation (`supabase/schema.sql`, `lib/server-crud.ts`, `lib/follow-up-engine.ts`, `app/pipeline/page.tsx`, `app/calls/page.tsx`).
- A real outbound email engine: sending mailbox pool, sequences and steps, enrollment state, scheduling windows, rolling caps, mailbox throttling, IMAP reply/sent capture, bounce and suppression handling, placement tests, delivery webhooks, AI reply classification/translation, operator reply drafting, and proposal-link generation (`lib/cold-email/`, `app/api/cron/`, `supabase/migrations/20260528_cold_email_engine.sql`, `app/inbox/page.tsx`).
- An outreach queue and job system with approval states, templates, attachments, scheduled jobs, campaign runs, delivery events, and quick-send/operator flows (`supabase/schema.sql`, `lib/email-jobs.ts`, `lib/outreach-workflow.ts`, `components/outreach/`).
- Personalised proposal pages and PDFs, signed HMAC tokens, claim capture, calculator events, PDF/open/page tracking, separate exporter and EU-importer variants, and an isolated public PDF host path (`app/p/[token]/`, `components/proposal/`, `lib/cold-email/proposal-link.ts`, `lib/proposal-analytics.ts`).
- A Meta WhatsApp Business integration with approved-template sends, personalised document headers, tracked links, inbound/status webhooks, reply classification, STOP/START opt-out handling, campaign caps, and an inbox (`lib/whatsapp/`, `app/whatsapp/`, `app/api/whatsapp/`, related migrations).
- Team messaging with founder identities, passcode login, DMs/channels, entity-pinned conversations, attachments, reply threads, reactions, unread/read state, in-app notifications, and Web Push (`supabase/migrations/20260623_team_messaging.sql`, `lib/messaging/`, `app/team/page.tsx`, `public/sw.js`).
- Website/company analytics: event collection, visitor/org enrichment, funnels, heatmaps, friction/error summaries, deploy markers, proposal events, website-lead capture, and CRM mirroring (`app/api/site-analytics/`, `lib/site-analytics.ts`, `app/analytics/page.tsx`, `app/website-leads/page.tsx`).
- A configurable integration registry with encrypted secret settings (AES-GCM), masked reads, and presets for Google Calendar, Aircall/dialer, WhatsApp Business, Gmail/IMAP, and Mailgun (`lib/integrations.ts`, `lib/integration-secrets.ts`, `app/api/integrations/`). In the current UI these are mostly settings/adapters; only WhatsApp and email/IMAP have deep provider behaviour.
- A personal Android/iOS Capacitor shell that loads the deployed web app (`mobile/`). It is a WebView wrapper for personal devices, not a distributed native product.

The “voice sales/customer management” surface is materially narrower than its name suggests. `components/calls/call-queue.tsx` and `lib/follow-up-engine.ts` provide prioritised call work, `tel:` or configurable Aircall-style URL launch, callback dates/notes, phone-number research, phone-history records, and call-outcome stage transitions (`app/api/leads/[leadId]/call-outcome/route.ts`). There is no telephony provider SDK, dialer session model, call recording, consent/retention policy, transcript, speech-to-text, AI call summary, voicemail, call disposition webhook, or voice agent. Aircall is a URL-template preset, not a call integration.

## Architecture and reusable assets

### CRM and company brain

`leads` is a wide, single-record CRM row containing company, one primary contact, phone/email, CBAM evidence, owner, stage, commercial dates, and outreach state. `activity_log`, `shared_tasks`, `lead_phone_history`, and `leads_audit` provide a useful operational timeline and rollback trail. `lib/follow-up-engine.ts` turns stage/date/activity signals into an urgent/high/normal/cold queue. `lib/import-reconciliation.ts` and `components/import/import-wizard.tsx` handle CSV/XLSX mapping, duplicate matching, constrained fields, and row-level import review.

These are strong reusable foundations for a configurable sales/customer-management core: Account, Contact, Opportunity, Task, Activity, Conversation, channel, and workflow concepts already exist in partial form. The data model needs to be split into explicit first-class entities before it can support many companies, multiple contacts per account, account hierarchies, custom fields, teams, customer success cases, and product-specific modules.

The current “brain” is mostly embedded in code and documents: CBAM stages and labels in `lib/types.ts`, CBAM estimates in `lib/cbam-estimates.ts`, proposal variants in `lib/free-quarter/` and `lib/importer-brief/`, campaign copy in `lib/cold-email/*`, and operating decisions in `docs/`. There is no tenant-scoped knowledge base, source citation graph, document ingestion/index, durable agent-run ledger, or general policy/rules engine.

### Revenue command centre

The dashboard, pipeline, call queue, inbox, campaigns, sequences, deliverability, proposal analytics, website leads, tasks, team chat, and analytics pages form a credible internal command centre. Key operational strengths are durable queue state, explicit `draft/ready/approved/sent` states, send windows/caps, suppression lists, signed links, idempotent-ish database records, and DB-level audit triggers (`supabase/migrations/20260715_critical_tables_audit_trigger.sql`, `supabase/migrations/20260715_leads_audit_trigger.sql`).

The command centre remains an internal system. It has no general workflow designer, event bus, outbox/inbox delivery contract, policy engine, tenant-level reporting, customer-facing workspace, or cross-company configuration layer. Several actions are still operator-specific and hardcoded to the CarbonSettle sales motion.

### Customer and channel management

Email is the deepest channel: the app stores inbound replies, sent-folder captures, mailbox identity, threading IDs, translated content, classifications, drafts, calendar invites, proposal links, and follow-up state. WhatsApp is the next most complete channel. Phone is a work queue with outcome logging. Team chat is internal collaboration, including contextual channels pinned to a lead or campaign. Website leads and proposal events bridge marketing activity to the CRM.

`integration_connections` stores provider settings globally by provider. Secret settings are encrypted with a key derived from `INTEGRATION_SECRET_KEY` or a Supabase key (`lib/integration-secrets.ts`). This is a useful adapter pattern, but there is no OAuth consent/token refresh, per-tenant connection ownership, sync cursor contract, provider replay/idempotency ledger, or provider-specific health/retry abstraction.

## Security, tenancy, permissions, and action safety

### What is present

- `proxy.ts` has a signed, app-wide HMAC cookie gate for non-public production paths; public proposal, unsubscribe, cron, webhook, analytics collector, and login paths are deliberately carved out. `lib/app-auth.ts` uses Web Crypto and constant-time comparison for the cookie signature.
- The messaging area has a separate passcode-backed founder identity flow (`app/api/auth/session/route.ts`, `lib/messaging/auth.ts`), membership checks for chat channels, and an HTTP-only session cookie.
- Supabase RLS is enabled on the baseline tables. `20260714_lockdown_rls_anon.sql` removes permissive anonymous policies and locks down importer data, mailboxes, push keys, research leads, and chat tables. The app relies on a server service-role client for server routes (`lib/supabase/server.ts`).
- Leads and critical sequence/importer tables have DB-level audit triggers and service-role-only audit sinks. The app also has campaign suppression, email status, scope, business-window, mailbox-cap, WhatsApp opt-out, and some atomic-claim guards.
- GitHub CI runs `npm ci`, the Vitest suite, and a Next.js build (`.github/workflows/ci.yml`).

### Gaps that matter for a SaaS product

1. **No tenant boundary.** There is no `organization_id`, workspace table, membership table, or tenant-scoped RLS predicate on CRM, outreach, integrations, proposals, tasks, analytics, or importer tables. `owner` is an enum (`Raghav`/`Aryan`) and `lib/workspace-scope.ts` is an application-level owner filter, not isolation. `integration_connections.provider` is globally unique. The migration itself calls the cold-email model “single-tenant” and says to tighten it later (`supabase/migrations/20260528_cold_email_engine.sql`).
2. **Authentication is shared/operator-oriented.** The main gate is one shared password/cookie, not a user/session/role system. Team-chat passcodes are separate from app access, and the session cookie on `main` stores the username directly (`app/api/auth/session/route.ts`, `lib/messaging/session.ts`). Role checks are not consistently enforced on CRM mutation routes. A SaaS version needs a real identity provider or signed user sessions, organization membership, role/capability checks, and tenant-aware route helpers.
3. **Server-role concentration.** Most API routes use the Supabase service role and therefore bypass RLS; route-level authorization must be perfect. That is difficult to audit when routes accept caller strings such as `performedBy`/`createdBy` and when actor identity is not derived from a verified user session.
4. **Public webhook policy is uneven on `main`.** The generic integration webhook accepts a missing secret because its comparison is conditional (`app/api/integrations/webhooks/[provider]/route.ts`). The WhatsApp verifier returns `true` when `WA_APP_SECRET` is unset (`lib/whatsapp/cloud-api.ts`). The non-merged `context-project-review` branch adds fail-closed webhook handling and constant-time secret comparison; this is a high-value candidate to port after review.
5. **Secrets have had unsafe transport options.** On `main`, several operational routes accept bearer secrets in query strings, and the generic webhook also accepts `?secret=` (`app/api/cold-email/archive-ingest/route.ts`, `app/api/cold-email/backfill-inbox/route.ts`, `app/api/integrations/webhooks/[provider]/route.ts`). The non-merged security branch removes query-string cron secrets, adds constant-time comparisons, decouples auth/proposal signing keys, and refuses service-role fallback in production (`origin/claude/context-project-review-0x0i6g` at `d288e75c14dce50150f9787149a79e5fe4bd271c`).
6. **Action idempotency and approvals are incomplete.** The queue/campaign paths have useful states and guards, but manual reply scripts in the email branches explicitly have no idempotency guard and can resend if invoked twice (`scripts/send-segment-a-followups.ts`, `scripts/send-via-prod.mjs` on `c3e7029f5ba29c32ce61e19e95d40de99513098b` and `c31432de8435492ab0f9152c6c0bd2340fd0c6a0`). A general product needs an action intent, idempotency key, approval record, policy evaluation, provider receipt, retry/dead-letter state, and immutable actor identity for every outbound action.
7. **The baseline README is stale.** `README.md` still says the schema allows anonymous read/write for a fast MVP, while later migrations remove those policies. New operators could follow the wrong security instructions.

## Testing and operational maturity

The repository has 11 test files covering selected route mocks and pure logic: activity KPIs, reply classification, campaign helpers, follow-up priority, import reconciliation, outreach sync, server CRUD, store behaviour, and three API routes. CI runs tests and build. There are no browser end-to-end tests, no real Supabase/RLS isolation tests, no tenant/role matrix, no webhook signature/replay tests, no provider contract tests, no email/WhatsApp delivery sandbox tests, no mobile-native tests, and no voice path tests. The branch `context-project-review` adds meaningful tests for proposal links, rendering, unsubscribe tokens, templates, workspace helpers, and route guard behaviour, but is not merged at the audited `main` tip.

The audit did not run tests or builds by design. Treat the presence of CI as evidence of intended checks, not evidence that this checkout currently passes them.

### Branch-level conclusions

- Of the 20 non-main heads, 8 are fully merged historical heads (zero unique commits at their tip), 12 retain branch-only commits, and two pairs are duplicate/overlapping families: Lane A (`claude/data-hunt-lane-a` and `data-hunt/A`) and the mobile/chat fixes (`claude/mobile-apps` and `fix/team-chat-reaction-mobile`).
- The only substantial unmerged runtime/security branch is `context-project-review`; its changes are valuable but include deletions/archival moves and should be cherry-picked by capability with tests rather than merged blindly.
- The data-hunt branches contain research payloads, not product functionality. Their own reports repeatedly state candidate-only, no DB writes, and no sends. They are useful for source-quality rules, provenance fields, domain dedupe, licence gates, and adversarial-review workflows.
- The client-acquisition, proposal, negotiation, partner, and startup heads are documents/collateral. They do not establish a reusable knowledge system or customer-management feature.
- The mobile family demonstrates a real app shell and strong internal collaboration UX, but it still loads one deployed web URL and has no tenant-aware native identity boundary.

## Reusable patterns for a shared SaaS core

1. **CRM lifecycle:** extract Account/Contact/Opportunity/Task/Activity/Conversation from `leads`, `shared_tasks`, `activity_log`, `lead_phone_history`, and outreach tables; retain stage-history and audit triggers.
2. **Action orchestration:** generalise `email_jobs`, `sequence_enrollments`, `outreach_events`, queue statuses, cron workers, mailbox leasing, provider receipts, and suppression checks into a channel-neutral action runner with idempotency keys and approval policies.
3. **Conversation spine:** unify email threads, WhatsApp replies, internal chat, phone/call events, and future voice sessions behind Conversation/Message/Participant/Channel records. Current inbox and team-chat code offer useful UI and threading patterns.
4. **Evidence/provenance:** reuse import runs, row audits, domain/evidence fields, source licence notes, and soft-quarantine concepts for any external research or AI-enriched record.
5. **Knowledge/agent layer:** promote `docs/` and CBAM-specific calculators into tenant-scoped sources, document chunks, citations, playbooks, agent runs, tool calls, approvals, and human feedback. Keep domain modules (CBAM, study-abroad, etc.) as configuration/packages rather than hardcoded lead fields.
6. **Mobile delivery:** the Capacitor wrapper, mobile nav, push setup, and responsive layout fixes can ship as a shell around a tenant-aware web app. The current personal-use URL-loading design is not an enterprise mobile distribution model.
7. **Document artifacts:** `scripts/render-proposal-pdf.py` and the KNL invoice renderer show a practical HTML→PDF pipeline with deterministic templates, missing-field warnings, and visual output. Add tenant storage, access controls, versioning, and generated-artifact audit records before reuse.

## Priority gaps to resolve before calling this a SaaS product

1. Introduce organization/workspace, membership, verified identity, roles/capabilities, and tenant-aware RLS. Remove owner enums as the security boundary.
2. Add Account/Contact/Opportunity/Customer/Case/Conversation entities and configurable fields/stages/playbooks. Keep the existing CarbonSettle fields in a CBAM module.
3. Build a channel-neutral action ledger: intent → policy check → approval → idempotency key → provider dispatch → receipt/webhook → retry/dead letter → immutable audit.
4. Add real voice: provider adapters, call-session state, recording consent, encrypted media retention, transcripts, summaries, next-action extraction, human review, and inbound/outbound event correlation. `tel:`/Aircall links are only the starting adapter.
5. Make integrations tenant-owned and production-grade: OAuth/token refresh, encrypted credential rotation, sync cursors, replay protection, provider health, retries, rate limits, and contract tests.
6. Port the useful `context-project-review` hardening selectively: fail-closed webhook/auth checks, no secrets in query strings, dedicated signing keys, production service-role refusal, send-time scope/suppression checks, and its tests.
7. Expand verification to browser journeys, RLS/tenant tests, auth/role matrices, webhook signatures/replays, provider sandboxes, action idempotency, mobile shell smoke tests, and voice tests.
8. Keep research and client artifacts separated from runtime seed data. Import only through a reviewed, tenant-scoped pipeline with source, evidence URL, licence, confidence, reviewer, and rollback metadata.
