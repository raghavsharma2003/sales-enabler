**Date:** 2026-09-21 (Asia/Kolkata)  
**Source:** `raghavsharma2003/html-portfolio`, all 31 non-symbolic `origin/*` heads after `git fetch --all --prune`. No source checkout, source script, provider, or product code was run. This is design research only; it does not authorize importing source code.

## Correction to the first pass

The earlier inventory was useful for branch names and tips, but it understated the strongest code path by treating it largely as a companion demo and by describing branches instead of tracing the runtime. There is a real browser voice application with a durable memory/relationship backend and offline gates. There is also a later, separate voice-clone/studio stack with concrete provider adapters and source-cited materialization. These are **reference implementations**, not evidence that a customer-facing sales product is complete, deployed, affordable, or suitable to copy.

The major correction is scope, not a claim of readiness: the strongest companion code is Meera/Maya-specific; its durable relational model is a dyad, not an account/team/company model. Its later clone stack is substantially implemented but its own latest handoff labels some live SQL/runtime work pending.

## What the tests and checked-in results actually establish

* `evals/echosim/*` builds the real `liveCall.ts` for simulated acoustic runs. `context/measurements.md` in `main` records 8 seeds per coupling and reports reduced self-duck/uplink after an echo change. That is simulation evidence, not a browser/device field result.
* `evals/recall/run.mjs`, `evals/consolidation/run.mjs`, `evals/rupture-channel/run.mjs`, `evals/rupture-lapse.mjs`, `evals/resilience/run.mjs`, `evals/trace/run.mjs`, `evals/persona-invariants.mjs`, and `evals/agent/isolation.mjs` are source-backed deterministic or DB-gated checks. They support contracts and regressions, not sales outcomes.
* The stored `docs/audit/2026-08-22-hinglish-tts.md` and `context/measurements.md` contain historical test claims. `evals/speech/l1-hinglish.mjs` is explicitly skipped unless `SPEECH_RUN=1`; do not treat its corpus as a completed current benchmark.
* The newer `evals/voice-bakeoff/plan.mjs`, `voice-code-switch-frontier/*`, and delivery-holdout paths are evaluation plans/harnesses. A plan, cost arithmetic, fixture, or a passing fake-adapter contract is not a provider-quality result.
* `claude/vyakti-cloning-platform-aq05n4`'s tip says runtime and live SQL validation remains pending. That status overrides any inference from its substantial code volume.

## Design implications for the product mock

1. Preserve the useful boundary: one compiled experience/context object, provider-neutral speech adapter, transcript/turn trace, and an exclusive audio-owner state machine. Do not import the companion persona, dyadic defaults, or raw prompts.
2. Treat voice character as separate inputs: textual register policy, pronunciation/text front-end, synthesis style, and interruption timing. The source proves these must be tuned separately; it does not prove a Hindi/English mix will work for a sales audience.
3. For a company relationship layer, keep source, scope, correction, revocation and who-authorized-what explicit. The source's strongest lesson is structural provenance and pre-retrieval disclosure filtering, not its relationship labels.
4. Put realtime behaviors in the mock as capabilities with observable states: listening, assistant speaking, interruption detected, reconnecting, fallback voice, and failure. Do not present emotional inference or an affect score as an established customer fact.
