# AI-assisted campaign brief (v6)

The campaign planner keeps its manual intent fields and adds an optional **Draft the brief with AI** action. It becomes available only after an operator chooses a current approved product or service, writes a campaign goal, and explicitly selects at least one existing customer. A successful proposal fills the existing desired outcome, evidence, audience rationale, and information-to-collect fields. The operator can edit every suggestion and must still choose **Generate campaign plan** separately. The brief step never creates, applies, or launches a plan or campaign.

`POST /api/campaign-brief` uses the configured `runAiTask` planning lane with a stable client request ID. Normal retries reuse that ID; the UI exposes a separate, explicit new-attempt action. `GET /api/campaign-brief?requestId=…` lets the browser reconcile a completed persisted proposal after a partial network failure. A replay with different input is rejected. A pending or uncertain request is not automatically retried.

The server first requires the exact offering revision shown in the planner, then atomically claims `platform:campaign_brief_proposal` under the current operator membership, approved offering, exact offering-source quotes, and selected-contact records. It repeats those compare-and-set fences when completing the proposal. The saved record binds the offering revision and digest, normalized goal, exact selected contact IDs, and the offering's exact source references. If the offering, a source, the selected audience, or operator access changes before or during inference, the proposal cannot complete.

Customer identity and CRM fields are not sent to the model. The model receives only the number of explicitly selected contacts, the approved offering fields, the operator goal, and the offering's exact source quotes. Contact IDs remain a server-side binding. Exact quote validation proves where the offering evidence came from; it does not prove that a selected customer used, bought, wanted, or consented to the offering.

The response allowlist is limited to a nullable outcome, bounded evidence requirements, a nullable audience rationale, bounded questions to collect, and bounded missing-context questions. Unknown fields and obvious personal identifiers are rejected everywhere. Affirmative audience claims about use, interest, eligibility, history, or consent are rejected, while questions and explicit uncertainty about those still-unknown facts are allowed. The server labels every accepted rationale as an operator-selected audience suitability hypothesis and states that use, purchase history, interest, eligibility, and consent remain unverified. When the goal is ambiguous, the model may leave suggestion fields empty and ask missing-context questions; the UI shows those questions without inventing values.

If validation rules improve after an AI receipt has completed, **Recheck saved output** reparses that same tenant-scoped receipt under the current rules. It performs no inference and revalidates current operator access, offering evidence, and selected contacts before changing an invalid proposal to ready.
