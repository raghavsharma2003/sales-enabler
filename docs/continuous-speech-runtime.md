# Private continuous speech runtime

The existing Node voice gateway now accepts application-authorized private recognition at `/private-speech`. The existing public `/voice` protocol remains separate. Run the gateway with `npm run voice:gateway`; its HTTP `/health` response reports the service and private speech capability without connecting to Azure. Configuration presence and gateway health do not establish provider access or microphone quality.

Configure `CONTINUOUS_SPEECH_GATEWAY_URL` with an exact `wss://…/private-speech` URL, and set `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION` only on the server. The application issues one-use, origin-bound tickets against a live private Azure microphone call after explicit consent. Azure credentials and Azure bearer tokens never go to the browser. Local loopback testing can explicitly set `CONTINUOUS_SPEECH_ALLOW_LOCAL_WS=true`; the issuing application also restricts the browser origin to loopback when using local insecure transport. No query parameter credentials are accepted.

The client sends `{ "type": "start", "ticket": "…" }`, followed by binary 640-byte frames: 16 kHz, mono, signed little-endian PCM16, 20 ms per frame. `{ "type": "stop" }` ends only recognition. SDK resources are allocated after the durable ticket claim, with authority checked again before starting recognition. A `ready` status means the authorized adapter accepts PCM. It does **not** mean Azure recognition has finished connecting: SDK startup can require the first PCM frame before its success callback. A separate ten-second startup deadline stays active until that callback. Failure closes the sidecar without reconnecting or shutting down the native voice call.

The gateway caps each session at 600 seconds and 19,200,000 submitted PCM bytes, paced at 50 frames per second with a bounded 25-frame (500 ms) burst to tolerate network or main-thread jitter. The bucket refills by one frame per 20 ms; the burst allowance does not permit sustained overspeed or unlimited buffering. It limits concurrent transports to 20 and private recognition to one per user by default, alongside the authority layer's durable lease. Authentication and input-idle deadlines are five seconds; each completed authority check schedules another within two seconds, and a pending periodic check has a two-second deadline. WebSocket messages are capped at 8 KiB; client output backpressure ends recognition above 32 KiB. Disconnect, authority revocation, expiry, provider errors, duplicate starts, invalid input, and shutdown all close allocated resources. Late authorization/allocation callbacks cannot restart an ended session.

`microsoft-cognitiveservices-speech-sdk` is a pinned **production dependency at 1.52.0**. The runtime imports this installed package; it never reads the historical ignored `data/probes` installation. The gateway is a separate Node process and requires its normal production dependencies in addition to the web application's artifact. When bundling a gateway entry point remotely, include/bundle this dependency according to that runtime's existing packaging process. No local container workflow is required, and this increment does not establish remote packaging or hosted deployment readiness.

The SDK exposes no public end-to-end send-buffer counter, and its audio pump drains the push stream without awaiting downstream sends. Two isolated, version-specific guards cover that boundary. `speechPushBufferedBytes` reads only queue length, chunk size, and partial-byte count. `guardSpeechTransport` reserves conservative byte counts for SDK messages until each send settles and also reads the owned Node socket's `bufferedAmount`. Combined push input, same-tick writes, pending send reservations, and socket-buffered bytes are capped at 64,000 bytes. Metadata includes byte or character counts and header lengths; content is never retained or logged by the guard. Unsupported factory, message, queue, or socket shapes fail closed. Cleanup terminates the SDK's owned socket even when SDK send promises stall.

Node 24 provides a native global WebSocket, which SDK 1.52.0 selects by default and which lacks `terminate()`. The server adapter configures the pinned SDK's `WebsocketMessageAdapter.forceNpmWebSocket` setting before creating connections, selecting the SDK's own Node `ws` transport so immediate cleanup remains possible. It does not replace or remove the process-global WebSocket. A local-only compatibility test opens an actual SDK `WebsocketConnection` against a loopback WebSocket server with the native global still present, sends synthetic bytes through the real SDK formatter, and verifies that guard cleanup closes the server peer. No Azure connection or inference is involved.

Compatibility tests construct the installed SDK and exercise its actual `sendAudio` pump against a synthetic transport whose sends never settle. The reproduction verifies closure while push input remains small, preventing the earlier downstream accumulation. Separate tests cover a growing socket buffer, mixed upstream/downstream pressure, invalid shapes, and 500 ms input bursts. These tests make no Azure connection. **Any SDK upgrade must revalidate both guards and the startup/cleanup lifecycle before changing the version pin.** The provider disables telemetry and configures the pinned SDK's connection retry count to zero; a disconnect closes the adapter rather than requesting reconnection. SDK utterance/replay bookkeeping is separate from stalled transport queues and remains subject to the session's absolute PCM/duration cap; this guard is not a claim that the entire SDK heap is limited to 64,000 bytes.

Hypotheses contain a sidecar session epoch, an internal utterance segment counter, a monotonically increasing revision within that segment, text, and sample offsets on this recognizer's submitted PCM timeline. Azure's 100 ns ticks are converted to samples, and non-finite, negative, oversized, or implausibly ahead-of-input offsets terminate recognition. Partial and final offsets can differ, so provider result IDs or offsets do not define segment identity. Text is capped at 4,000 characters; interim callbacks are capped at ten per second, and excessive aggregate result callbacks fail closed. No hypothesis history is accumulated. A `sidecar_final` is only this recognizer's result, not the authoritative native-call transcript or permission to generate a response or execute a tool.

English (India) and Hindi (India) are supported. An authority with both recognition languages uses the SDK's documented language autodetection constructor. This does not establish Hindi/Hinglish code-switch accuracy. The adapter never logs raw SDK errors, audio, recognition text, or provider payloads. Closure persistence is limited to bounded duration, PCM byte count, hypothesis count, and an allowlisted reason. Local mocked-provider WebSocket tests cover the lifecycle and resource boundaries; they do not prove live Azure recognition, acoustics, physical microphones, latency, interruption quality, or production readiness.
