# Integration setup and actual capabilities

The integration catalog lists available **server adapters**, not tenant connections. A manually configured connection starts as `needs_setup` when its credential is saved. `check` calls a fixed provider endpoint and sets `connected` only after a successful response. An expired token or missing permission may still fail on a later pull, especially where the identity endpoint does not test every data scope. `error` records a safe status message. Read syncs stage untrusted source material for human review; they do not directly create contacts, approved knowledge, or communication consent.

Manual setup accepts access tokens and private app tokens. Manually supplied Google and Microsoft access tokens expire and require reconfiguration and a new check. A separate Google/Microsoft OAuth flow can securely store refresh tokens when app credentials are configured (see below). Never paste provider credentials into chat or project documentation.

For OAuth, configure `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` or `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET` on the server; `MICROSOFT_TENANT_ID` is optional and defaults to `common`. `APP_URL` must match the public origin in production. The redirect endpoint is the fixed `/api/integrations/oauth/callback`; availability is returned by `GET /api/integrations/oauth/setup`, and an owner starts authorization with same-origin `POST /api/integrations/oauth/start` using `{integrationId,allowSend?}`. The flow uses PKCE, one-time state, encrypted refresh tokens and refresh-on-expiry. See [OAuth setup](oauth-setup.md) for provider console steps. `allowSend` is only meaningful for Gmail or Microsoft Mail and is separate from any later approval or customer channel consent.

Set `CONNECTOR_ENCRYPTION_KEY` in the **server** environment to a random 32-byte value encoded as 64 hexadecimal characters. Keep it outside source control and back it up securely. Changing or losing this key makes existing connector credentials unreadable; reconfigure those connections after an intentional rotation. The server refuses credential configuration when the key is missing. Connector secrets are AES-256-GCM encrypted with tenant and connection identity as authenticated data. They are stored in `integration:vault` entities, outside `/api/platform` and `/api/workspace` record listings. Only the first user in a workspace, currently its owner, can manage integrations. Multi-user role administration has not been implemented.

## API

`GET /api/integrations` returns `{ catalog, connections }` for the signed-in workspace owner. Connection objects include status and non-secret settings, never tokens or encrypted ciphertext.

`POST /api/integrations` requires a signed-in owner, JSON, and same-origin request. It accepts:

```json
{ "action": "configure", "integrationId": "hubspot", "credentials": { "token": "PRIVATE_APP_TOKEN" } }
```

Other actions are `check`, `sync`, and `disconnect`, each with `integrationId`. `configure` replaces the prior secret and returns `needs_setup`; it never calls the provider. `disconnect` removes the credential immediately. `sync` makes a bounded read of up to 15 provider items and stages each new item as an ingestion source for human analysis and review. Gmail, Google Drive, Dropbox, Notion and Intercom fetch full content for at most five items per sync; the remaining entries carry metadata and an explicit `contentStatus`. Repeated item IDs with the same source update time are skipped. A connection change or disconnect interrupts the remainder of an in-flight sync at its next checkpoint; this is a synchronous request, not a background job queue.

For manual Gmail or Microsoft Mail configuration, `credentials.sendPermission` may be supplied only as the exact provider scope `https://www.googleapis.com/auth/gmail.send` or `Mail.Send`, respectively. It is a user assertion about the supplied token, not proof of provider scope or permission to contact a customer. OAuth connections set that field only when the send scope was explicitly requested and granted. Provider enforcement, operator approval and current channel consent still apply to any outbound action.

The catalog is extensible through `lib/integrations/catalog.ts` and a corresponding fixed-origin adapter in `lib/integrations/adapters.ts`. Adding a catalog entry alone does not create a connection.

## Generic incoming webhook

Configure and check `generic_webhook`, then use the returned `webhookPath` on this deployment's origin. POST a JSON **object** with a unique `X-Integration-Event-Id` (1–200 letters, digits, `.`, `_`, `:`, or `-`). Set `X-Integration-Signature` to `sha256=` followed by the lowercase hex HMAC-SHA256 of the exact raw request bytes, keyed with the configured secret. Payloads above 1 MiB are rejected; accepted payloads above 200,000 characters are staged as marked excerpts. A valid new event returns HTTP 202 and stages a source; a replayed ID returns HTTP 200 with `accepted:false`. Signature errors return HTTP 401. Secret rotation or disconnect invalidates older signatures. The webhook payload is untrusted source material and cannot directly create contacts, consent, approved knowledge, or external actions.

Provider checks and syncs are read-only and use fixed HTTPS hosts, eight-second timeouts, no redirects and a 1 MiB cap on each provider response. List calls use one page, and selected content calls have the explicit count limits above. Provider errors are reduced to safe HTTP status messages; raw upstream bodies are never sent to the browser or logs. Real provider connectivity remains untested until a workspace owner supplies credentials and explicitly runs `check`.
