# Voice evidence lab

The Quality page contains an evidence workflow for saved browser call transcripts. Its purpose is to produce inspectable, limited findings rather than a voice quality leaderboard. The existing Test Lab remains a separate configuration and knowledge authority check.

## Workflow

1. Select a versioned scenario. The 20 cases in `evals/scenarios.json` appear as seed rubrics. An operator can edit one into a new immutable version or author a new rubric with a name, language, scenario, expected outcome and 1–8 observable criteria. Earlier assessments retain their rubric snapshot.
2. Select a saved call with a transcript and run an assessment. The server loads it from the authenticated tenant, captures its transcript, provider, input mode and agent configuration snapshot when available, and calls `runAiTask` with `task: 'evaluation'` and `responseFormat: 'json_object'`. The AI task router supplies a durable tenant scoped claim, budget accounting, model and token receipt. The evaluation service separately claims the operator request ID before calling AI. A pending or uncertain run is not automatically retried.
3. Inspect the original model response, criterion verdicts and exact quotes. A scored model verdict requires a quote of 4–450 characters that occurs verbatim in the stated transcript entry. Duplicate/missing criterion IDs, malformed JSON, invalid indices and invented quotes invalidate the whole assessment. Acoustic or timing criteria cannot receive a scored transcript-only verdict. Invalid runs keep their model receipt, raw response and reason but no judgments. Older assessments retain their original parsed judgments; the list API reads full response text from the tenant-scoped AI task receipt when available.
4. Review each criterion as an operator. Choose `met`, `not_met` or `uncertain` and record a reason after checking the quoted source and saved transcript. The review is an append-only record linked to the assessment, criterion, rubric version, source, transcript digest and operator. It never overwrites the model verdict. This matters because a model can return a verdict that contradicts its own rationale, especially for negated criteria.
5. Optionally record a separate human 1–5 rating with the criterion, operator ID, note and whether the operator heard audio. Ratings are distinct from operator adjudication of a transcript assessment. A transcript-only rating does not establish acoustic quality.
6. Optionally import a competitor trial with vendor, scenario version, transcript, source label, input mode, notes and declared comparison conditions. This is always labeled `operator_imported_unverified`. Import does not call a vendor API or prove vendor identity.

## Comparison protocol and limits

The UI asks for a pair ID and the same language, script version, network profile, device, knowledge snapshot, components and input mode on both arms. It matches completed assessments only when those declarations, scenario version and pair ID agree. **Raw AI judgments never enter comparison denominators.** A criterion contributes only when both sides have explicit, decisive operator reviews; `uncertain` and unreviewed sides are excluded. Descriptive percentage-point differences require at least three such matched pairs for that criterion. Missing review coverage, own conditions, imported trial assessments, pair IDs and unmatched own calls are visible. A comparison is still based on operator declarations and unverified imported transcripts, so it is not causal or proof of vendor superiority.

The lab cannot measure acoustic naturalness, pronunciation, latency, VAD/endpointing, interruption timing, playback, or actual external side effects from browser submitted text. Received timestamps are not speech event timestamps. For a defensible voice claim, use consented audio, synchronized traces, predeclared outcomes, blinded human listening and the broader protocol in `research/2026-09-22/voice-quality-benchmark.md`. This implementation intentionally does not infer those results from text.

## Storage and API

`GET /api/evaluations` lists tenant scoped scenarios, imported trials, assessments, append-only operator reviews, ratings and a descriptive comparison. `POST /api/evaluations` accepts `scenario.create`, `trial.import`, `assessment.run`, `assessment.review` and `rating.create`. POST requires authentication, JSON and the same browser origin. Records live in the existing `entities` and `audit_events` tables under `eval:*` kinds. Assessment review rechecks tenant ownership, criterion membership and source transcript linkage before saving. Session and agent version reads are tenant scoped. Assessment requests are idempotent by tenant and request ID; reusing an ID with different input returns a conflict.

No claim of a live competitor run or audio test is created by this API. Each assessment is an operator initiated Azure evaluation text task, so it consumes the configured task budget and records actual model/token usage.
