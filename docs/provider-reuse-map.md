# Provider and relational voice reuse map

22 September 2026. Static source audit only. No source application, provider call, credential, browser microphone, or live deployment was exercised for this audit. Code locations below are repository-relative to the named read-only source. Existing branch inventory and `research/html-second-pass.md` cover lineage and the broader product; this note traces the mechanisms the current implementation can use. The user's current constraint is that the **only paid calls may use the supplied Azure FoundersHub resource and its $5,000 grant**. Google AI Studio key-pool code and OpenRouter code remain reference designs or later optional lanes; their historical configuration in another product is not authorization to spend here.

The `html-portfolio` audit covers all 31 remote heads via the existing branch ledger and a fresh blob check of the routing files. The latest `_gkeys.js` and `_lanes.js` blobs occur in `main` and `voice-cloning`; 29 other heads share an earlier version of each. `_azure.js` is the same blob across all 31. The successor Foundry budget file has three distinct blobs across 29 heads and the structured dialogue adapter has two. The pinned rows below use the later, more complete code for each mechanism instead of counting inherited copies as separate implementations.

## Relational and emotional voice seams

`origin/main:src/engine/compiler.ts:compile` and `src/engine/memory.ts:prefetchCallContext` create one contextual prompt for the call; `api/memory.js:opRecall/opForget` and `api/_disclosure.js` supply filtered memories. `src/engine/relstate.ts` (`8047589e2ea21ee968f5623d3651450cb4625a50`) implements event-based honorific, trust and rupture/repair movement; `ruptureRepairShift` requires the other person's repair signal rather than the assistant's guess. These are implemented *dyadic companion* rules, not validated business relationship scores. Use the provenance, asymmetry and correction principles for customer journeys; do not port intimate trust scoring or persona history as business facts.

`origin/codex/handoff-history-20260909:api/_voice/hindi-text-frontend.js:buildVoiceTextPlan` (`4d3b3a8c5e7c44b5b229e79c9cb97ce644549547`) separates pronunciation planning from dialogue. `origin/main:evals/speech/l1-hinglish.mjs` is an opt-in TTS→STT round trip, not current quality proof. `src/voice/liveCall.ts` has detailed acoustic logic and `evals/echosim/*` simulation; neither establishes Azure WebRTC acoustic performance. A business voice evaluation must measure interruption, turn completion, Hindi/English pronunciation, disclosure, factuality and customer outcome on the selected Azure deployment.

## Selective ports now, ranked

1. **Azure grant guard and provider error taxonomy.** The current `sales-enabler/lib/voice/server.ts` already connects Azure Realtime and maps some HTTP statuses; `lib/voice/config.ts` validates the browser endpoint. Add a shared Azure resource/paid-provider invariant for all model tasks and a structured classification of quota, configuration, transient and unknown outcomes. Keep credentials server-only. This is the narrowest useful port while honoring the user's paid-call rule.
2. **Azure spend reservation and usage receipts.** Adapt `_provider-budget.js` to the existing organization and record store, with stable request keys, configurable grant allocation, actual deployment rates, reservation, settlement and uncertain-outcome reconciliation. A $5,000 credit is a ceiling to monitor, not an assumed zero-cost unlimited lane.
3. **Task-aware model routing and trace.** Put browser voice, response generation, extraction, embeddings and transcription behind separate capability contracts. Record requested task, selected Azure deployment, attempts, status class, elapsed time, usage and fallback reason; avoid secret material. Do not make the source's Google/OpenRouter ordering the default here.
4. **Voice continuity and evaluation.** Implement one owner for audio and one durable turn ID across interruption/reconnect; use source `useCallEngine` as a reference. Add a real-device Azure evaluation before tuning echo/turn thresholds or claiming Maya/Meera-like voice quality.
5. **Free Google pool only as a later guarded experiment.** The keyring and resilience code are proven as code, but this workspace has no verified free pool, per-key independent quota, usage authorization, provider privacy decision or live quality result. A future free lane can be enabled by explicit configuration while the paid fallback remains Azure; optional billed Google and paid OpenRouter paths stay disabled.

Current implementation status: `sales-enabler/lib/voice/config.ts`, `server.ts` and `browser-session.ts` support one configured browser voice provider per session. Azure Realtime is selected through the user's existing resource, with two completed saved browser Listen & type transcripts and a separate bounded synthetic-audio server smoke test. Microphone capture, STT and interruption remain unverified because the microphone request timed out before connecting; there is no cross-provider fallback or Azure grant ledger. This audit should guide selective implementation and not be read as a claim that the source's past production measurements transfer to this app.

Two source traps matter during a port: `_lanes.js` classifies all HTTP 403 responses as quota even though its prose describes some 403 cases as deterministic; the new adapter should classify a response using provider-specific error codes where available. Also, `_lanes.js` applies its deadline signal only after the first free-pool attempt, so an initial hung request can exceed the nominal four-second budget. Enforce the deadline from the first outbound request.
