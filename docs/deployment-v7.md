## Runtime shape

The Node 24 Debian container has five explicit targets: `web` runs Next standalone on port 3000; `worker` runs the durable schedule loop; `channel-worker` processes authorized queued AI channel replies; `learning-worker` prepares authorized conversation-learning proposals; `voice-gateway` runs the optional public WebSocket relay on port 3001. Every runtime uses the unprivileged `node` user. Compose adds an init process, drops capabilities and grants shutdown time. Next startup explicitly validates configuration and runs the existing additive `CREATE TABLE/INDEX IF NOT EXISTS` bootstrap before accepting requests. This is not a versioned migration system. Next standalone static assets and `public` are copied explicitly, following the installed Next deployment guide.

The worker is off unless both its Compose profile and `AUTOMATION_WORKER_ENABLED=1` are selected. The web process always has `AUTOMATION_WORKER_ENABLED=0`. Enabled schedules can perform external delivery; enable the worker only after reviewing the actual schedules and connector authority. Its default local restart policy is off, so an unexpected stop requires operator review. Never interpret a provider-uncertain delivery as a safe retry.

The channel worker is independently off unless the `channels` profile and `CHANNEL_WORKER_ENABLED=1` are selected. Its script also enforces this gate outside Docker. It has no ingress or published port, shares the same persistent database and connector vault, and may generate Azure replies and perform authorized external sends when enabled. Its durable `channel-worker` heartbeat is checked separately from email scheduling. Both worker flags remain off in web and voice containers.

The learning worker is independently off unless the `learning` profile and `LEARNING_WORKER_ENABLED=1` are selected. This is a global feature gate: app/gateway/channel processes also receive the opt-in value so authorized completed conversations can enqueue learning jobs; only the separate learning worker processes the queue. Every process defaults to `0`. Azure `enableLearningWorker=false` controls both the shared flag and the optional no-ingress container. Enabled channel/learning processing requires the existing Azure endpoint, key and explicit text deployment name at readiness. Learning keeps generated proposals subject to review; enabling its process does not approve proposals or permit paid retries of uncertain work.

The optional voice profile supplies `/voice` WebSocket ingress and `/health` liveness. Set runtime `PUBLIC_VOICE_GATEWAY_URL` on the web service to `ws://localhost:3001/voice` locally or the final `wss://.../voice` externally. The application registry checks exact published origins; the gateway has no environment bypass for that authorization. Azure Realtime credentials remain server-side. A live health probe does not prove the voice provider or database is healthy; verify a reviewed deployment/session flow separately. Gateway source and end-to-end evidence are documented by the public voice implementation.

Before packaging, run `node scripts/check-package.mjs` against the completed `.next/standalone` output (or supply one explicit output directory). It checks names/metadata only, requires `server.js`, and rejects environment artifacts, private data/backup directories, database/WAL/journal files and unexpected application links. It never opens file contents or logs offending names/paths, and it skips dependency internals. This is an application-artifact boundary check, not a source secret scanner or dependency audit. A tracing correction does not remove old output: clean the previously generated standalone directory through the checked build workflow before rebuilding, then require the checker to pass. Never ship an earlier failed artifact. Six focused fixtures verify missing/empty output, passing dependency fixtures, redacted failures, private trees, database sidecars and external-link refusal.

## Local containers

Put settings in a private ignored `.env.container.local`, never in the Dockerfile or build arguments. Minimum settings are `APP_URL=http://localhost:3000`, a stable random 64-character hexadecimal `CONNECTOR_ENCRYPTION_KEY`, and a separate stable 64-character hexadecimal `AUTH_LIFECYCLE_KEY`. Keep encryption keys separately backed up; changing them makes their existing ciphertext/tokens unusable. `VOICE_PROVIDER=none` supports account/company work without inference credentials. For Azure voice, set `VOICE_PROVIDER=azure` and the existing endpoint, key and Realtime deployment; configure the existing text deployment for text tasks. Public sessions need a separate `PUBLIC_SESSION_HASH_SECRET` of at least 32 characters; configuring a gateway URL without that secret fails readiness. No automatic non-Azure paid fallback is enabled.

Hosted email verification defaults on. Production readiness requires `AUTH_LIFECYCLE_KEY`, and when verification is required it also requires `AZURE_COMMUNICATION_EMAIL_ENDPOINT`, a valid base64 `AZURE_COMMUNICATION_EMAIL_ACCESS_KEY`, and `AZURE_COMMUNICATION_EMAIL_SENDER` from an existing authorized ACS Email setup. The HTTPS application origin must match the account-link origin. The local loopback Compose file explicitly defaults `AUTH_REQUIRE_EMAIL_VERIFICATION=false` for a preview without ACS; this does not validate email delivery or password recovery. The Azure template retains `true`. Missing ACS remains a public-launch blocker, and production startup reports only missing variable names. `AUTH_DEV_MAIL_OUTBOX` is development/loopback-only and is never a production delivery fallback. Configure `AUTH_TRUSTED_IP_HEADER` only after verifying that trusted ingress strips/sets that header; it is deliberately absent from the template defaults.

```powershell
docker compose --env-file .env.container.local config --quiet
docker compose --env-file .env.container.local up --build -d app
```

The base file binds only loopback and stores SQLite in the named `workspace-data` volume. It explicitly permits SQLite under a production Next build for **single-host local use**. Never use SQLite on Container Apps ephemeral disks, share it over network storage, or scale this configuration across hosts. `docker compose down` preserves the volume; `down --volumes` destroys it and is not part of this runbook.

Local PostgreSQL is an explicit overlay. Supply `POSTGRES_PASSWORD` and `DATABASE_URL=postgresql://workspace:URL_ENCODED_PASSWORD@postgres:5432/workspace` privately, then run:

```powershell
docker compose --env-file .env.container.local -f compose.yaml -f compose.postgres.yaml config --quiet
docker compose --env-file .env.container.local -f compose.yaml -f compose.postgres.yaml up --build -d app
```

PostgreSQL 17 uses its own named volume and has no published host port. Existing SQLite data is **not** migrated by changing `DATABASE_URL`. Only add `--profile worker` and start `worker` after privately setting its explicit enable flag. Add `--profile channels` and start `channel-worker` only after separately enabling reviewed channel replies. Add `--profile learning` and start `learning-worker` after explicitly enabling authorized background learning; recreate app/gateway/channel containers with the same global flag so they can enqueue. Add `--profile voice` and start `voice-gateway` when a reviewed public voice deployment needs it. Do not print full `docker compose config` with real secrets; use `--quiet`.

## Health and diagnostics

`GET /api/health` returns process liveness. `GET /api/health?ready=1` returns 200 only if configuration and a read-only database/schema query succeed; otherwise it returns generic 503. Neither response exposes variables, hosts, tenants, credentials or internal exception details. Probes never create a database or schema. Web readiness is intentionally independent of optional schedule-worker health.

```powershell
node --env-file-if-exists=.env.local --import tsx scripts/readiness.ts --config-only
node --env-file-if-exists=.env.local --import tsx scripts/readiness.ts
node --env-file-if-exists=.env.local --import tsx scripts/readiness.ts --worker
node --env-file-if-exists=.env.local --import tsx scripts/readiness.ts --channel-worker
node --env-file-if-exists=.env.local --import tsx scripts/readiness.ts --learning-worker
node --env-file-if-exists=.env.local --import tsx scripts/bootstrap-db.ts
```

The CLI reports issue codes and variable **names** only. Each worker check requires its own durable heartbeat within two minutes, separately from the web probe; select one worker per command. Learning heartbeats use service `learning-worker`, status `running`, a process-specific ID, and change to `stopped` on exit (including `--once`). PostgreSQL probes bound connection/query timeouts and close their own one-connection pool; SQLite opens read-only. A missing schema fails readiness instead of reporting a misleading healthy database. These checks do not verify authorization coverage, restore readiness, schema version, provider balance, active mailbox permissions, application write permissions or throughput. Azure's worker templates have no ingress and no HTTP heartbeat endpoint: configure external heartbeat alerts before enabling delivery. Docker health status alone does not restart an unhealthy container. A busy channel or learning pass can outlast the heartbeat window; distinguish stalled processing from a long bounded provider operation during load tests.

## Backups and restore drills

For local SQLite, use Node's online backup API rather than copying a live `.sqlite` file without its WAL. `scripts/sqlite-snapshot.mjs backup|restore ABSOLUTE_SOURCE ABSOLUTE_NEW_DIRECTORY` requires an existing parent, allocates a new private directory atomically, verifies source and snapshot integrity, and never overwrites or removes an existing destination. It opens the source read-only. A failed operation can leave its newly created directory for inspection; reruns must choose another new directory. Example paths below are illustrative, not actual customer data:

```powershell
node scripts/sqlite-snapshot.mjs backup 'C:\workspace\data\workspace.sqlite' 'C:\backups\workspace-2026-09-27'
node scripts/sqlite-snapshot.mjs restore 'C:\backups\workspace-2026-09-27\workspace.sqlite' 'C:\restore-drills\workspace-2026-09-27'
```

Restore creates a new verified database. Stop every web, worker and gateway process, verify the new store with fictional/read-only checks, then explicitly switch `SQLITE_PATH` or the local volume mapping. Never replace an open live database or its WAL files. Preserve the old store until the operator accepts the recovery. Back up the stable connector key through a separate secure path. Database files contain tenant data and credentials/ciphertext metadata: encrypt backups, restrict filesystem/cloud access and define a deletion/retention schedule. The scripts do not provide remote storage, scheduling, key escrow or retention enforcement.

For managed PostgreSQL, verify the actual provider's point-in-time retention and restore-to-new-server flow; run a restore drill in an isolated authorized database before promising any RPO/RTO. An operator may additionally use version-compatible `pg_dump --format=custom` with connection settings supplied through a secure environment/service file, then `pg_restore --no-owner --no-acl --exit-on-error` into a new empty isolated database. Neither utility nor a hosted restore was available/verified in this slice. Never pass a password-bearing URL in a logged command line. Do not restore over a running application database. [Node SQLite backup API](https://nodejs.org/api/sqlite.html#sqlitebackupsourceDb-path-options) documents the online snapshot mechanism.
