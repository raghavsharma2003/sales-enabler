# Sellability audit — 10 October 2026

Read-only source audit at `5249801`; no build, UI interaction, customer data inspection, provider call, or cloud change. Read `AGENTS.md`, `PRODUCT.md`, current `context/STATE.md`, operating-model and October 9 experience direction, then traced account, campaign, private voice, deployment, usage, and worker code. The 900-test record is useful local evidence, not proof of these commercial gaps being closed.

**Decision:** the product has credible paid-pilot foundations, but is not ready for unattended public self-service. The strongest immediate offer is an admitted consultancy workspace completing one counselling follow-up workflow with accountable human review. Keep its offering, language, columns, and context configurable in the general core.

## 1. Public account creation can expose shared paid inference without a commercial admission boundary

**Missing implementation; highest hosted blocker.** Registration creates an organization and owner once account email delivery is configured (`lib/server/auth.ts:71`, `lib/auth-lifecycle/service.ts:20`). Sign-in/registration throttling is a per-process, per-email map (`lib/server/auth.ts:49`); changing emails or instances does not share that bucket. Email verification *is implemented* and blocks normal workspace APIs (`lib/server/auth.ts:43`). This is not an authentication-is-absent finding: verified email is simply not a funded pilot entitlement.

After normal auth, consent, and context validation, private voice provisions Azure directly (`app/api/voice/connect/route.ts:44`). There is no durable tenant/user allowance, call-admission reservation, or cost ledger in that route. The 10-minute native private call limit is a browser timer (`lib/voice/browser-session.ts:316`); the short-lived secret at `lib/voice/server.ts:92` controls token validity, not a server-enforced conversation spending ceiling. The optional Speech sidecar has useful durable per-user concurrency and duration controls (`lib/voice/continuous-speech-authority.ts:148`), but those do not bound the underlying native Realtime call or total daily spend.

Text tasks have durable idempotency and an atomic daily token budget, but missing `AI_DAILY_ORG_TOKEN_BUDGET` means no aggregate cap (`lib/ai/task-router.ts:31`). Usage aggregates select only `ai:run` records (`lib/ai/usage.ts:23`), excluding voice. Public deployments already have durable concurrency, daily, and per-IP reservations (`lib/deployments/engine.ts:226`); retain these rather than duplicating them. Per-deployment limits alone do not establish a workspace/platform spending allowance.

**Smallest coherent hosted increment:** explicit admitted-pilot entitlement with a closed hosted default; finite text allowance; durable private voice admission/attempt allowance and concurrent lease, reserved before provider contact and retained conservatively after uncertain outcomes; owner-visible allowance and clear refusal. Do not describe minutes or rupees as enforced until a server-owned transport/provider call-control path can actually terminate native voice. If that control cannot fit this increment, gate hosted private voice explicitly rather than representing the client timer as a spending control. Test concurrent requests, abandoned sessions, provider uncertainty, inactive membership, and exhausted allowances with zero unintended provider invocations. A payment checkout is not needed to admit and invoice the first pilot manually.

## 2. The first useful campaign still requires reconstructing context across workspaces

**Missing workflow implementation, not missing core capability.** A fresh Home recommends company description, first source, first agent, publication, then public channel; New campaign is a secondary alternative (`lib/platform/workspace-journey.ts:266`, `:274`, `:298`, `:316`). Exact saved campaign resume is implemented (`:296`). Company can save its description as an unreviewed Brain source (`components/platform/company-view.tsx:57`), and campaigns have useful missing-offering/customer links (`components/platform/campaigns-view.tsx:235`, `:243`). These are real foundations.

The decisive break is Agent & content: browser mode offers only an active release selector (`components/platform/campaigns-view.tsx:248`). With none available, the founder must leave, assemble agent instructions, test, publish, remember the original campaign, return, and manually choose the result. No campaign-to-agent-to-campaign context handoff is present in this surface. The October 9 direction explicitly proposes that missing path; a proposal is not implementation.

**Smallest coherent buyer increment:** from the saved campaign, “Prepare an agent for this campaign” carries its goal, selected approved sources, editable language, and exact return reference into a proposed draft. Explicit save, existing checks/rehearsal/publication, then “Use this release in [campaign]” updates that same campaign through revisioned save. Keep campaign facts distinct from global agent configuration. Preserve the return path through reload, failed save, and stale campaign revisions. Add direct prerequisite returns for source/offering review where needed, without imposing a public deployment on a private first campaign.

Acceptance is one *new empty workspace* completing company context → one source/offering → reviewed customer rows → saved counselling follow-up campaign → agent preparation/test/publication → same campaign run → accepted evidence-backed next-step/obstacle fields and an owned follow-up. Existing source/result validators already preserve uncertainty (`lib/campaign-results/service.ts:19`, `:138`); reuse them. A second industry configuration should not require a schema change.

## 3. Customers cannot yet rely on channel follow-through being operated and diagnosable

**Both an implementation gap and an external evidence gap.** Workers, durable jobs, uncertain-send handling, and heartbeat records exist. Automation exposes recent worker liveness (`lib/automation/engine.ts:149`); channel processing writes a heartbeat (`lib/channel-agents/service.ts:364`); CLI readiness has individual worker checks (`scripts/readiness.ts:6`). Do not claim that scheduling or channels are unimplemented.

However, public application readiness calls `checkReadiness()` without worker requirements (`app/api/health/route.ts:9`). A ready application does not establish operational reply/learning workers. Learning's tenant UI distinguishes the environment's enabled flag, not a currently running worker (`components/platform/deployments-view.tsx:531`; `lib/learning-jobs/engine.ts:113`). Channel health lacks the equivalent tenant-facing recent-worker/oldest-waiting-job explanation. A configured but dead worker can leave the buyer looking at durable queued work without a useful diagnosis.

**Smallest coherent operating increment:** a tenant-scoped operational status attached to Deployments and queued outcomes: worker enabled/running/stale, last successful pass, oldest eligible waiting work, uncertain outcomes, and an explicit owning recovery action. Preserve conservative no-resend semantics. Worker readiness remains independently checkable; do not break the ordinary application liveness probe to hide missing process supervision.

**External gates:** an approved host and PostgreSQL runtime, verified account-mail sender/delivery, worker supervision, real chosen-channel credentials/webhook routing, and one accepted inbound/reply plus human-handoff receipt. Code cannot invent these. WhatsApp inbox supports bounded replies but explicitly excludes templates and campaign sends (`components/platform/inbox-view.tsx:72`); do not sell proactive WhatsApp outreach from that surface. Native phone calls remain deferred. Physical microphone, Android, interruptions, perception, and actual customer value still require direct evaluation; current typed/synthetic proofs do not establish them.

## Recommended next decision

Complete the campaign→agent→campaign handoff as the next product slice while keeping hosted signup closed until paid-inference admission is implemented. Then operate one admitted pilot through one chosen customer channel with truthful worker status and retained delivery/outcome evidence. These three connected gaps matter more to the first invoice than another optional voice research feature or a larger test total. No source or benchmark evidence currently supports claiming superiority over Vapi, ElevenLabs, or Bolna.
