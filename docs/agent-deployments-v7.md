# Agent deployments v7

The deployment registry is a separate publication boundary around an existing immutable agent version and its active tested browser release. The release's existing check proves configuration and source authority only; it does not establish voice quality, microphone behavior, live provider delivery, or customer outcomes. Public agents use the configured Azure resource and provider-default profile. The private Maya profile remains unavailable for public deployment.

## Owner flow and API

`GET /api/deployments` returns `{deployments}`. `POST` accepts `create`, `publish`, `pause`, and `stop`; mutations require a current owner membership fence. Create inputs are `name`, `agentId`, `versionId`, `releaseId`, `channel` (`web_voice`, `web_chat`, `telegram`, `whatsapp`), `publicKnowledgeIds`, explicit `brand: {name,welcomeMessage}`, `allowedOrigins`, `limits`, and optional `allowUnknownInbound`. Provider identities and authorization versions are derived from the checked server vault. Drafts have no outbound effects. Creating or publishing a Telegram deployment does not install a provider webhook; that is a separate explicitly acknowledged activation operation.

Optional create input `autoLearning` is a strict boolean and defaults to `false`; older records without it remain opted out. Only explicit `true` authorizes automatic learning **proposals**, never automatic approval or promotion. The choice is frozen in the owner-created deployment snapshot; status transitions preserve it and changing it requires a new reviewed draft. Learning workers must require explicit true in both the issued snapshot and current deployment, match the revision, and include fresh deployment authority fences in their reservation. It is not included in anonymous public metadata or prompt context.

Publish, pause and stop require `deploymentId` and current `revision`. Publish additionally requires `publicationAcknowledgement` exactly equal to exported `PUBLICATION_ACKNOWLEDGEMENT`: “only selected approved company sources are public”. The UI must make this acknowledgement an explicit owner decision. A stopped record cannot be republished. Draft snapshots are immutable; changing settings means creating and reviewing a replacement draft. All mutation roles are owner-only, including pause and stop.

`platform:agent_deployment` stores the public snapshot and references. Secret capabilities, nonces, counters, provider bindings and issuance markers use non-platform entity kinds and cannot enter ordinary platform record listings. Only explicitly authored brand copy is public; no organization profile or private description is automatically copied.

## Public context boundary

The selected public sources must be a subset of the immutable version's knowledge IDs. At publication and every use, all version source digests must still match approved records, the exact configuration test must pass, and the exact release must remain the current active release binding. The server compiles only selected complete sources. It never reads customer records, customer memories, commitments or GroupAI. Effective configuration overrides knowledge IDs to the selected subset, memory scope to `none`, tools to an empty list, and profile to provider-default. The reviewed agent instruction text remains part of the server context, so owners should review those instructions for public suitability too.

The anonymous public view contains only opaque public ID, channel, public brand, AI disclosure, availability and bounded conversation limits. It does not expose the compiled agent configuration, source bodies, provider keys, vault data, tenant ID or owner identity. Visitor-supplied IDs cannot select a canonical customer.

## Sessions and bounded usage

`getPublicDeployment(publicId,origin)` returns the sanitized view after authority checks. `issuePublicSession(publicId,{origin,ipAddress?,requestId?,purpose?})` creates a short-lived capability and nonce, returning `{token,nonce,sessionId,expiresAt,deployment}`. Capability and nonce are persisted only as hashes. A supplied issuance request ID is one-use; retrying an issued request returns an honest conflict because plaintext tokens are not retained for replay. The public route should require a stable request ID. Purpose is `voice` or `chat`; a web-chat deployment cannot issue voice authority. Web-voice can issue separate chat sessions for fallback, with both counted against the same deployment budgets.

`resolvePublicSession(token,{origin,purpose?,consume?,nonce?})` rechecks fresh authority and TTL, returning server-only context/configuration, deployment, publisher actor, session ID and expiry. `consume:true` requires the current nonce, atomically increments the turn count and returns a replacement nonce; concurrent or repeated use loses the compare-and-set. Consumers must check the expected purpose and consume before generation/provider setup. A voice gateway must additionally reserve one exclusive activation per capability, maintain a hard provider connection timeout, and recheck fresh authority while open. Continuous audio/token cost is bounded by that gateway's session timer; registry turn counts alone do not meter audio tokens.

Defaults: usage disabled, 25 sessions per UTC day, 12 turns per conversation, 3 concurrent sessions, 300 seconds per session, and 3 issuances per network bucket per UTC hour. Hard configurable maxima are 500/40/10/600/10 respectively. Durable issuance epochs and counter compare-and-set statements serialize reservations across instances. Closed, expired and invalidated deployment-revision sessions do not consume current concurrent capacity. Pause/republish never resets daily or network budgets. `closePublicSession` authenticates the token hash and exact original origin to close a capability idempotently even after expiry or deployment revocation; it cannot return context or grant provider authority. During republish, an old voice provider connection can briefly overlap a new revision's slot until the gateway's two-second authority recheck closes it; the hard session expiry still applies. Counter and replay receipts persist as audit/replay protection; retention pruning must preserve the current budget windows and active capability authority.

Set private server environment `PUBLIC_SESSION_HASH_SECRET` to a stable high-entropy value of at least 32 characters. It HMACs network addresses; raw network addresses are never stored. A host must sanitize forwarding headers before passing a trusted address. When no trusted address is available, callers share a conservative `unknown` bucket. Changing the secret rotates network buckets and should be an operational action, not a per-process default.

Allowed origins are exact HTTPS origins or local HTTP loopback origins, without paths, wildcards or trailing slash. The normalized server `APP_URL` origin is also allowed for standalone pages and requests made by an iframe hosted on the app itself. Each issued capability remains bound to its exact issuance origin. Server-only `getPublicFrameOrigins(publicId)` checks current publication, source and publisher authority and returns only explicitly configured embedding origins for the host's `frame-ancestors` CSP; it does not add `APP_URL` to the customer frame-parent list. The host must fail closed if that helper rejects. Origins constrain browser use; they are not visitor identity or authentication. Anything approved for anonymous use is public to a non-browser client that can supply those request headers. CORS is not a confidentiality boundary.

## Worker authority

`resolveDeploymentForConnection(user,{deploymentId?,channel,connectionId,authorizationVersion,identity})` requires exactly one matching published deployment, a current publisher owner membership and authorization version, and the exact live vault connection. Telegram binds its checked bot ID; WhatsApp binds its phone number ID. Reauthorizing, replacing, disconnecting or changing account identity invalidates the deployment. Publisher role withdrawal/removal invalidates it, and restoring membership with a new authorization version does not revive old authority. An owner must review a new deployment.

The returned `DeploymentAuthority.fences` must be included in the same database transaction that reserves any public/scheduled provider generation or external send. `deploymentTurnStatements(authority,{conversationKey,eventId})` supplies durable daily/conversation caps and one-use event reservation; include these statements with the authority fences and the worker's own claim. Each send after generation must resolve fresh authority again. A previous resolution is not permission for future egress. `allowUnknownInbound` defaults false and allows a channel worker's conservative inbound service path only when explicitly set; it grants no private customer context or outreach consent.

## Local verification

`tests/deployments.test.ts` covers public knowledge scoping and private-context exclusion; forged/cross-origin/cross-purpose capabilities; nonce and issuance replay; concurrent issuance, daily, network and conversation caps; expiry, pause and stop; changed sources and releases; transactional source/membership/connection races; member restoration; cross-tenant references; default-off usage; owner-only mutations; exact provider identity and authorization binding. Tests use fictional resources and perform no external calls. Live delivery, production PostgreSQL behavior and provider voice quality remain separate verification work.
