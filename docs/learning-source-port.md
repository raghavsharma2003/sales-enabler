# Source-grounded conversation learning

This port adapts the exact-source authority boundary in `api/_room-memory-authority.js` at `origin/claude/vyakti-cloning-platform-aq05n4` (`6d7d9bcd4f9c4c793e8db34b70ac03d874fe8d4a`, file blob `fe35bd7294c282b09f72b51672c12c8b5e126fb1`). Its `validateRoomMemoryProposal` requires a source ID and an exact contiguous quote from a user row, then its commit SQL checks source and authority again. The Room correction path creates a replacement only from an explicit new user statement and records the superseded fact. This implementation keeps those boundaries in the company workspace's existing SQLite/Postgres entity store, with tenant/session IDs in place of Room follower/epoch IDs.

`POST /api/conversation-analysis` accepts a saved `sessionId` and `requestId`. The server reads the tenant-owned transcript and a small tenant/contact-scoped context snapshot; client-supplied transcript text is never analyzed on this route. It sends bounded turns to the existing Azure-only `runAiTask` feedback lane. The prompt permits feedback themes, practical concerns, stated preferences, caller corrections and commitment requests. It excludes assistant promises as fact evidence, mood or diagnosis labels, trust scores, and invented completed work. Each returned card is checked against an included caller turn's exact quote and stored with its turn index and character span. The analysis stores a session digest and IDs of context excerpts used. Invalid cards are omitted; an empty result is valid.

The analysis request ID is claimed durably before the model call, and the underlying AI task router owns one counted Azure attempt. A replay returns the prior analysis state. The final write compares the saved session bytes inside the same transaction that commits cards. If the conversation changes during the model call, zero cards are committed and the analysis is marked stale. Failure or uncertain model state is retained under that request ID; the caller must use a new request ID after review.

`POST /api/conversation-analysis/[id]` applies selected reviewed card IDs at a required revision. It rechecks tenant ownership, session bytes, contact binding, and every exact caller quote. A compare-and-set transaction changes card state and creates proposed legacy customer memories or proposed manual actions. An operator can submit `reviews: [{candidateId, reviewedType, destination}]` to correct a model classification or destination without another AI call. The server accepts only known types and destinations, requires a linked customer and a reviewed preference or correction for memory, and rejects extra review fields such as a replacement quote. Original model labels and exact source quotes remain stored alongside the operator classification and an audit event. Corrections carry `correctionRequiresReview`; they do not revoke or silently replace an existing approved memory. Commitment requests create manual action proposals and do not assert that the company accepted or fulfilled them. Feedback cards kept as feedback remain conversation-linked evidence; private caller data is never promoted to company-wide knowledge. No memory approval, action completion, or external send occurs. Duplicate application returns the same IDs without another write.

Apply also has a narrow deterministic refusal guard for explicit English declines such as “I do not need a follow-up call,” “I don't want any call,” and “No follow-up please.” A card with that exact caller evidence cannot create a manual follow-up action even when an earlier model verdict or operator type calls it a request. The API returns 409 with instructions to keep it as conversation feedback or, for a linked customer, explicitly review it as a preference. The UI defaults these cards to feedback, shows the refusal notice, and does not change consent or create permanent memory. The guard deliberately does not match “Don't hesitate to call” or “I did not receive a follow-up,” because those are not refusals.

The existing Customers memory approval transition now revalidates learning-derived memory lineage. It requires the current tenant-owned session digest, linked contact, exact caller turn and quote. The session data, status and creation timestamp are fenced in the same transaction as the memory status change; the memory row's data preimage is fenced too. Missing, revised, cross-tenant, or assistant-origin evidence leaves the memory proposed. Legacy staff-authored memories without learning lineage follow their prior review behavior.

The extraction prompt checks each caller turn independently for explicit language, pacing, address and channel preferences, concrete human/team follow-up requests, concerns and corrections. It permits multiple cards from one turn when the intents differ and caps output at eight cards within the feedback task's token budget. The Conversations component shows the model quote, type, interpretation, reason, and destination, then lets an operator explicitly choose the reviewed meaning and destination before selecting a card. Customer memory review requires the operator to choose stated preference or caller correction; the interface does not silently relabel a concern. The source transcript remains browser-submitted and its receipt timestamps do not establish speech timing. Focused tests cover exact quotes, assistant-origin rejection, tenant scope, request/application idempotence, correction review, source mutation, and operator overrides. The upstream Room migration and live SQL were not imported or run.
