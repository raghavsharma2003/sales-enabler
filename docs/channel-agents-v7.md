# Private Telegram and WhatsApp agents

Implemented locally, 27 September 2026. No real bot, Meta number, external recipient or live channel delivery was used during verification.

## Setup and operation

1. Configure Azure text inference, connector encryption, the shared database and a public HTTPS `APP_URL`. Set `AI_DAILY_ORG_TOKEN_BUDGET` for a workspace-wide ceiling. Channel inference uses the existing Azure task router, with a conservative 50,000-token daily fallback if that environment setting is absent. No paid fallback provider is enabled.
2. In Integrations configure Telegram `token` and `webhookSecret`, or WhatsApp Cloud credentials. Telegram connection check verifies `getMe`; its checked numeric bot identity is bound to the deployment. Secrets remain encrypted in the vault.
3. Create and test an immutable agent version, publish its release, then create and publish a Telegram or WhatsApp deployment selecting only approved public company sources. Exactly one published deployment may resolve for each channel connection. Unknown WhatsApp senders require the owner's explicit `allowUnknownInbound` choice; it defaults to false.
4. Telegram's separate **Activate webhook** operation checks `getMe` and `getWebhookInfo`, then installs the expected HTTPS callback with `secret_token` and `allowed_updates: ["message"]`. A different existing webhook requires the explicit replacement acknowledgement. The saved installation receipt records the last provider confirmation; changes made later in Telegram are not monitored. WhatsApp uses the existing signed Meta webhook and business-number binding.
5. Run a supervised worker with the same database, encryption and Azure environment as the app: `node --env-file=.env.local --import tsx scripts/channel-worker.ts`. `--once` performs one bounded tick. Run it as a service/container alongside the web application; it is not started by an HTTP request. The worker writes the `channel-worker` heartbeat.

`GET /api/channels` returns private operator threads and installation receipts; `?threadId=` includes bounded thread history. Owner activation, operator handoff and Telegram operator replies use same-origin authenticated POST actions. The panel allows Pause AI, Enable AI, and a durable Take over and send reply. WhatsApp operator replies continue through the existing inbox and its original customer/consent guards.

## Authority and isolation

Telegram accepts authenticated private text messages only. Groups, guest/business updates, edited messages, media and bots are ignored. The callback checks the secret header before reading a streamed body bounded to 512 KiB. A Telegram account ID or WhatsApp phone is a channel participant, not verified human identity or automatic customer linkage.

The native Meta webhook authenticates its raw body and business number before saving an inbound receipt. The channel hook consumes that original server-saved receipt, including on provider replay; it never treats client-submitted reply text as incoming authorization. Public company replies stay within the verified 24-hour WhatsApp service window. Cold outreach, templates and automatic marketing consent are unavailable. Existing linked-customer phone and contact restrictions remain fenced even for company-only AI replies.

Workers resolve the current deployment, exact publication revision, original publisher authorization, release, source digests and encrypted connection before both inference and provider egress. All captured authority plus thread state is checked in the same database transaction as the claim or final dispatch reservation. A completed pause, stop, source change, reauthorization or operator takeover defeats an earlier pending reservation. A provider call already authorized and in flight cannot be recalled.

The answer uses public deployment instructions and only the selected approved sources. The existing RelationalOS runtime replays bounded history from this same private participant/thread, plus the current message, under the published language/style settings. It derives explicit address, language, pacing, repair and correction behavior without importing CRM memory or writing preferences globally. Every generated reply carries AI disclosure. Missing facts must be acknowledged; configuration and mocked tests do not prove that a model will never produce an unsupported statement.

Exact stop/unsubscribe and direct human requests pause automation conservatively; quoted commands and questions such as “Are you human?” do not themselves trigger handoff. Both requests persist while a deployment is paused. Ordinary inbound text and republishing do not clear human handoff; an operator must explicitly use Enable AI. Durable off-ramp receipts prevent a provider replay from reversing that later operator choice. An operator cannot clear a participant stop through Enable AI. Phrase coverage is authored and bounded, not a claim of universal multilingual intent recognition.

## Durability, limits and recovery

Each provider event has one stable tenant/connection-scoped job ID and immutable input digest. Conflicting Telegram replays fail closed. One atomic generation claim and one dispatch reservation permit at most one provider attempt per job. Telegram manual replies retain their request ID across an HTTP retry. Azure generation uses the router's own idempotent receipt and shared token ledger.

Limits include 200 queued/generating/sending jobs per tenant, 30 attempts per participant/connection/day, published deployment daily conversation and per-conversation turn caps, and published concurrent-session capacity. Jobs expire after 15 minutes or the inbound service window, whichever is earlier. A full queue still accepts participant stops. Concurrent uncertainty holds both the thread and deployment slot for review.

Stale generating/sending claims become `uncertain` after two minutes. A timeout, unparseable receipt, mismatching Telegram recipient or ambiguous server response never causes automatic resend. Inspect provider history before resolving uncertain outcomes; this slice deliberately has no blind retry/unlock action. Accepted means the provider accepted the message, not that a recipient received or read it. Native WhatsApp operator delivery receipts remain separate from channel AI acceptance receipts.

Channel jobs retain private inbound text, reply, source/version selection, provider identity, AI run and server-derived behavioral evidence. Each terminal AI exchange also creates one immutable canonical `session` (`source: channel_chat`) linked to its deployment for Conversations and reviewed learning. It includes only that incoming turn and a provider-accepted assistant turn. Uncertain attempted text is separately marked unconfirmed and excluded from the delivered transcript. No customer ID is inferred, no whole-thread transcript is repeated, and no private chat is automatically promoted to Company Brain.

Automatic learning proposals are a separate opt-in. Each inbound job freezes the deployment's `autoLearning` choice and publication revision when it is enqueued. After the canonical exchange and terminal delivery receipt commit together, the server may enqueue a learning job using that frozen authority, subject to `LEARNING_WORKER_ENABLED=1` and the learning worker's current authority and budget checks. Later enabling the setting does not retroactively opt earlier messages in, and there is no historical scan. A learning enqueue failure cannot change an accepted delivery, remove its transcript or trigger another send. Proposed feedback still requires operator review; it never automatically becomes company knowledge or customer memory.

## Local verification

`node --import tsx --test tests/channel-agents.test.ts tests/messaging-whatsapp.test.ts` covers authenticated Telegram callbacks, body bounds, private-chat filtering, conflicting replay, tenant isolation, concurrent claims, public-only grounding, handoff and operator takeover races, deployment/source/connection/publisher revocation, expiry, stale recovery, stop persistence, private history scoping, canonical exchange provenance, relational cue reuse, daily and queue caps, unknown WhatsApp opt-in, and unchanged manual WhatsApp guards. All inference and provider sends are injected fictional responses. PostgreSQL execution, live hosting, worker recovery under infrastructure loss, real bot/Meta delivery and physical mobile usage remain unverified.

Provider reference: [Telegram Bot API](https://core.telegram.org/bots/api) (`getMe`, `getWebhookInfo`, `setWebhook`, `sendMessage`) and [Meta's WhatsApp Cloud API collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api). The current Meta documentation endpoint returned HTTP 429 during this implementation, so existing verified 24-hour service-window behavior was preserved rather than claiming fresh live Meta validation.
