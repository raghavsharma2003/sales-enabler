# Team access

The Team & access screen supports owners, operators and viewers. Owners invite, change roles, remove access and revoke pending invitations. The last active owner cannot be removed or demoted. Ownership is never automatically transferred. Operators can perform normal company work; viewers can read but cannot mutate workspace state or invoke POST-based AI/voice provider operations. Integration management is owner-only, including OAuth callbacks.

New registrations atomically create the company, account, owner membership and durable original-owner claim. Legacy companies receive that claim for their first user ordered by creation time and ID. Other legacy users do not acquire implicit membership. Demotion/removal does not rerun ownership selection. Webhooks use a currently active owner.

Invitation links expire in 72 hours, are email-bound, single-use, and only their SHA-256 digest is stored. The raw link appears only when created; owners must copy and share it themselves. No email is automatically sent. The token uses a URL fragment, is removed from browser history after opening, and is submitted in a JSON POST body to avoid access-log/referrer leakage. An existing account must authenticate using its password or a matching signed-in identity. A different signed-in email must sign out first. An account bound to another organization is rejected, even when it was registered after invitation issuance. Invite possession verifies control of the invitation channel; ordinary account registration does not provide independent email-delivery verification.

Each authenticated request checks active membership in the database. Removal also deletes existing sessions; role changes take effect on the next request. Already-authorized in-flight business operations are not globally canceled. Background workers must recheck active operator/owner access immediately before execution. Logout remains available to all sessions. Service callers handling privileged actions use the current-membership helpers rather than cached role fields.

Team changes and invitation acceptance use one tenant epoch compare-and-set plus an atomic database batch. This serializes changes across processes and protects last-owner checks, invitation replay and concurrent acceptance. A conflict fails with a refresh/retry response rather than silently overwriting access. Audit entries record invitation, acceptance, role changes and removal without raw invitation tokens. Membership/invitation records use private `team:*` entity kinds and are excluded from generic product entities.

Current limitations: email is globally unique and an account belongs to one workspace. There is no multi-workspace switching, organization transfer, email delivery, SSO, independent email verification, or account recovery flow. The per-process authentication limiter still requires shared infrastructure for public multi-instance deployment. PostgreSQL follows the same transactional fence but remains unverified in this local pass.

Verification: `npx tsx --test tests/team-access.test.ts` exercises role boundaries, provider mutation denial, owner demotion, session removal, explicit re-admission, email mismatch, cross-workspace rejection, expiry/revocation/replay, concurrent acceptance, simultaneous owner demotions and deterministic legacy ownership.
