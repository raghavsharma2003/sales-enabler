# Company source ingestion and review

An operator can stage paste or webhook text with `POST /api/ingestion` JSON `{title, text, kind, format?}`. Multipart upload accepts `{title?, file}` for UTF-8 TXT, Markdown, CSV, JSON, HTML and EML, plus text-based PDF and DOCX. `GET /api/ingestion` lists the tenant's sources. `GET /api/ingestion/:id` returns `{source, job?, proposal?}`. Analysis uses `POST /api/ingestion/:id` with `{action:"analyze", requestId}`. Review uses `{action:"apply"|"reject", revision, candidateIds}`; reject may omit `candidateIds` to reject all unreviewed candidates.

The source artifact is tenant scoped and immutable by this API. It stores a SHA-256 digest, original text (or original PDF/DOCX bytes as base64), extracted text, and stable 2,800-character blocks with absolute offsets. HTML is converted to inert text: tags, scripts, styles, frames, SVG and templates are removed. The parser never follows URLs. Uploads are capped at 512 KB. Sources and extracted text are capped at 240,000 characters; PDF is capped at 30 pages, and DOCX archives at 200 entries and 4 MB declared expanded size. A scanned PDF without text returns an explicit OCR-required error. None of these formats execute embedded code or macros.

Analysis sends at most six chunks of four blocks (67,200 characters) to the configured `runAiTask` extraction route. The proposal reports analyzed/total chunks and omitted characters. Each candidate must cite a 3–600 character exact contiguous quote from one named block. The server checks the quote and absolute span against saved text; malformed JSON, fabricated quotes and unsupported shapes are omitted with an operator-visible note. Source text is marked untrusted in the model instruction. The prompt classifies standing procedures and recurring agent instructions as company facts or FAQs; `action` is reserved for a specific new task. Contact suggestions should quote the name and email together when available. Candidates carry confidence and uncertainty as model opinions, not authority. Duplicate or conflicting candidates are flagged against the same proposal and existing company knowledge. Contacts use their separate customer-record review; feedback and one-off actions remain review-only. No extraction grants consent, sends communication or creates executable actions.

A deterministic scope guard flags structured individual records such as `Name: …; Email: …` or CRM name/phone fields as `possible_customer_record`. A generic company support address alone does not trigger it. The guard is evaluated when a proposal is read and again at knowledge apply, so proposals saved before the guard cannot silently publish a customer record as a company fact. `POST /api/ingestion/:id` with `{action:"classify",revision,candidateId,type,reason}` lets an operator correct an unreviewed suggestion to `contact` without another model call; an unflagged one-off action may also be corrected to a standing company fact or FAQ. The server preserves `modelType`, `modelQuote`, original `quote` and source span, appends a bounded type-review history, and audits the compare-and-swap update. Personal record evidence cannot be upgraded to company knowledge through this action. Once corrected to `contact`, the separate customer-record review form becomes available.

Apply is an explicit operator action. It checks tenant, source status/digest/revision, proposal revision, quoted spans and current approved brain sources plus legacy knowledge for duplicate titles or content. Only selected, issue-free offer, company fact and FAQ candidates can be applied. The proposal transition and all selected canonical `platform:brain_source` inserts commit in one database transaction with audit events. Every canonical brain writer (`brain.create`, `brain.update`, `brain.approve`, `brain.revoke`, and ingestion apply) advances the same tenant catalog revision in its transaction. Ingestion captures that revision before scanning for duplicates; if another brain write commits first, its transaction fails with 409 and must review the new catalog. Manual approval also checks duplicate approved titles/content. Each new source has `approved` status, revision 1, title/content, source label, author, approval actor/time, and source artifact/digest/quote/span/proposal IDs. The response's `applied` IDs and each candidate's compatibility field `appliedKnowledgeId` identify these brain-source records. Campaign planning and voice context can select them immediately; the existing `brain.revoke` path can withdraw them. No legacy `knowledge` row is created. Retries of a completed selection return its original brain-source IDs. A stale or conflicting selection returns 409. Rejection is similarly recorded and leaves source and brain untouched.

Contact candidates have a distinct operator step at `POST /api/contact-import` with `{sourceId,candidateId,revision,name,email?}`. The server reloads the tenant source and latest proposal, rechecks the exact quoted span, and requires the entered name and optional email to appear in that quote. It checks effective customer details, including active profile overrides. An exact email or name match returns 409 with a same-tenant existing customer ID for direct navigation; no fuzzy match or automatic merge occurs. A successful review atomically creates one canonical `contact`, a durable import receipt, and candidate status `linked_customer` with `linkedContactId`. The contact stores quote/digest/source provenance and `identityVerified:false`; it has no consent grant or customer profile. Retry of the same reviewed intent returns the original customer. Imports, manual customer creation, and customer profile identity updates all advance the same tenant customer-directory revision in their write transaction after capturing it before identity lookup. A concurrent create or email change therefore forces one side to refresh rather than silently create an exact duplicate. Exact name conflicts require operator review; this is not an identity merge or a fuzzy match.

## Reused source patterns

The exact-quote and bounded-batch rule adapts `ROOM_MEMORY_BATCH_CAP`, `ROOM_MEMORY_EXTRACTION_SYSTEM`, `validateRoomMemoryProposal`, and `runRoomMemoryConsolidation` from the read-only `research-sources/html-portfolio` branch `origin/claude/vyakti-cloning-platform-aq05n4`, file `api/_room-memory-authority.js`. There, a proposal quote must be a contiguous substring of its specific source row, and the SQL commit rechecks source authority after model execution. Here, `parseCandidates` checks a saved block and `reviewIngestion` rechecks the immutable artifact and proposal in the atomic apply transaction. The subject taxonomy is different: company facts, offers, FAQs and review-only operational leads.

The review separation adapts `research-sources/command_centre/app/api/import-review/route.ts` and `lib/import-review.ts`: import rows with `review_required` are resolved deliberately, with distinct audit outcomes. This port does not reuse that product's lead classification, company identity matching, or outbound messaging. No source repository file was modified.

The PDF parser follows [pdf-parse's local buffer and `getText` API](https://github.com/mehmet-kozan/pdf-parse/blob/main/README.md); DOCX extraction follows [Mammoth's `extractRawText({buffer})` API](https://github.com/mwilliamson/mammoth.js/blob/master/README.md). Both operate on bounded uploaded buffers, with no remote URL supplied to either parser.
