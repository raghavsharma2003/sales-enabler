# Connected email campaign delivery

This port adds an operator-triggered send to a saved `email` campaign run. Launch still creates only a reviewed queue. Each click on **Send email** calls authenticated `POST /api/campaign-delivery` for one recipient; the server creates a durable, tenant-scoped intent before provider egress. `GET /api/campaign-delivery?runId=…` returns that run's current recipient/receipt states. There is no automatic campaign send, telephone path, retry job or background dispatch.

## Source and adaptation

The idempotency key in `lib/delivery/key.ts` is a direct adaptation of Vyakti-GroupAI `origin/claude/vyakti-cloning-platform-aq05n4` at `451de5a6a7017dc76eaac69fe551203dc94753d2`, `packages/delivery-runtime/src/policy.ts`, blob `a48b75cc6684afeaecfd04f8345eb57f46953d47`: length-prefixed, SHA-256-bound material prevents one logical intent key from crossing tenant, provider, destination, run or mailbox boundaries. The one-intent state/recovery rules in `lib/delivery/engine.ts` adapt `packages/delivery-runtime/src/runtime.ts`, blob `c9aa0ae96d305fe269ce23ea5c5f5cfdbc3abd4f`, and its adversarial test, blob `ccd69ce6cd816caccdc182c93d0ef1773e25c4eb`. This app uses its existing SQLite/Postgres `entities` and audit transaction interface, rather than Vyakti's Postgres social-world schema. The full source runtime's leases, fences and reconciliation transport are not transplanted; this is one explicit synchronous send with durable ambiguity handling.

The send gate rechecks active run, initiating operator, exact queued recipient and snapshot address, current email consent/opt-out, approved plan sources, connected mailbox send permission and its launch-time **authorization version**. This opaque version changes on new manual credentials, new OAuth grants, send-scope changes and disconnect/reconnect. Health checks, sync timestamps and a refresh with the same verified OAuth scopes and mailbox identity keep it. A legacy connection without this version must reconnect before a new send run. The ordinary row revision still changes on health/refresh and is used as a short-lived compare-and-swap fence. The send path refreshes credentials if needed, re-reads the current connection, verifies its row revision and authorization version, then fences the relevant run/contact/profile/connection/plan/source row preimages and inserts the unique intent in one database transaction. A changed authority row blocks egress. The provider call follows that transaction; a process crash leaves `sending`, which the next status read marks `uncertain` after 60 seconds. Neither `uncertain` nor `rejected` can be automatically sent again from the same run recipient.

The vault connection's `sendPermission` setting is an explicit scope attestation; a manually entered token is still enforced by its provider. For OAuth connections, the stored confirmed scope list must include Gmail `https://www.googleapis.com/auth/gmail.send` or Microsoft Graph `Mail.Send`. OAuth connect and refresh also check the provider's own mailbox identity (Gmail profile email or Graph user ID), stored only inside sealed credentials; a different identity cannot inherit the run's authorization. `getUsableCredentials` refreshes expired tokens. A read-only connection with Gmail metadata or Graph Mail.Read cannot send.

Gmail uses `users.messages.send` with a UTF-8 MIME message in base64url `raw`. Address and subject are validated before constructing headers; the subject uses folded RFC 2047 encoded words, and the body is base64. Microsoft Graph uses delegated `/me/sendMail` with `Mail.Send`. Fixed provider URLs, no redirects, a 15-second bound and no token logging apply. Gmail's returned message ID and Graph's HTTP 202 are recorded as **accepted by provider**. Neither is evidence of delivery or reading. A timeout, network failure, 5xx, or malformed success acknowledgement is **uncertain**; a definitive 4xx is **rejected**. There is no automatic resend after uncertainty.

Provider references: [Gmail users.messages.send](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send), [Microsoft Graph sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0). Graph explicitly states that HTTP 202 means accepted for processing, not completed delivery.

## Verification and current boundary

`tests/delivery-email.test.ts` uses injected offline dispatch and stubbed fetch. It covers accepted-once/duplicate requests, timeout ambiguity without resend, a simulated crash after provider acceptance and recovery to uncertain, revoked consent, tenant isolation, manual credential replacement, same-grant OAuth refresh after a health check, send-scope loss, MIME header injection, Gmail message-ID acceptance, Graph 202 acceptance and a 503 uncertain result. `tests/integration-oauth.test.ts` and `tests/integrations-live.test.ts` verify OAuth/vault behavior with offline provider mocks. No real email was sent in verification.

Provider acceptance is the last verified state available here. Actual delivery, bounce, reply correlation, unsubscribe handling, inbox reconciliation and provider-native idempotency remain separate work. The current pre-egress authority transaction closes the ordinary stale-read window, but the existing DB interface cannot hold a privacy/consent lock across the external HTTP call; a future worker with a dispatch barrier should use the full GroupAI lease/fence contract before automated or bulk sending.
